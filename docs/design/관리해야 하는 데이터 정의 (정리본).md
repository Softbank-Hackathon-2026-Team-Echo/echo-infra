# 관리해야 하는 데이터 정의

BCDR 플랫폼이 백업·복제·복구 과정에서 다뤄야 하는 데이터를 정의한 문서입니다.
설계 근거는 데이터 정합성(ADR-0001)과 아키텍처 문서(CDC 백업·복구 파이프라인)를 참고하세요.

---

## 1. 기본 원칙

- **정적 데이터는 백업만 하고, 관련 인프라는 대기(standby)시키지 않습니다.** 거의 바뀌지 않는 데이터까지 예비 서버를 띄워두는 것은 낭비입니다.
- 다만 DB처럼 **계속 바뀌는 동적 상태**는 다릅니다. 이건 **RPO 목표에 따라** warm standby(평소에도 따라 돌려두는 대기 사본)를 둘지 결정합니다.
  - **RPO** = 복구 시 데이터를 어디까지 잃어도 되는가 (목표 유실 범위)
  - **RTO** = 복구에 걸려도 되는 시간
- RPO·RTO의 구체적 수치는 아직 정하지 않았습니다. (5장 참고)

---

## 2. 데이터 분류

관리 데이터를 다루는 방식에 따라 네 묶음으로 나눕니다.

| 묶음 | 성격 | 해당 항목 | 다루는 방식 |
|---|---|---|---|
| **A** | 계속 복제해야 하는 상태 데이터 | 1, 3, 5 | 지속 복제 + 백업 |
| **B** | 코드로 정의되는 데이터 | 2, 6 | Git·IaC가 원본 |
| **C** | 값의 위치만 관리하는 비밀값 | 4 | 비밀 저장소에 두고 참조만 |
| **D** | 파이프라인 메타데이터 | 7 | offset·카탈로그로 관리 |

위 1장의 "정적 데이터는 백업만" 원칙은 **A 묶음에만** 해당합니다.

## 4. 항목별 설명

### 1. 온프레미스 로컬 DB
- 애플리케이션에 부하를 주는 Trigger 대신, DB의 변경 로그(Binlog)를 읽는 **CDC**로 백업합니다.
- Binlog는 **ROW 포맷 + GTID**로 켭니다. (ROW = 바뀐 행을 그대로 기록, GTID = 복제 위치를 가리키는 번호)
- 복구에는 기준이 되는 전체 사진 한 장이 먼저 필요하므로, **주기적 Base Snapshot + 연속 Binlog** 두 트랙으로 저장합니다. Binlog만으로는 복구할 수 없습니다.
- 변경 이벤트는 Redis Stream으로 플랫폼에 전달합니다. Redis는 전달 통로일 뿐이고, 내구 저장본은 Object Storage에 둡니다.
- 전달은 at-least-once(중복 가능)이므로, 적용은 **멱등(Idempotent)**해야 합니다.
- 캡처는 **Debezium Server**로 합니다(ADR-0003). Binlog 파싱·초기 스냅샷·offset을 Debezium이 대신하므로, 직접 Producer를 구현하지 않습니다.

### 2. 컨테이너·워크로드 정보
- 원본은 "컨트롤 플레인 저장"이 아니라 **Git**입니다. 워크로드 매니페스트를 Git에 두고 Argo CD가 동기화합니다.
- 이미지는 바뀔 수 있는 Tag가 아니라 **Digest**로 고정합니다(`repository@digest`).
- 특정 레지스트리 종속을 피하려면 이미지를 다른 레지스트리로 복제합니다(ECR → GCP Artifact Registry, 또는 온프레 Harbor).
- 접속 URL·배포 위치 같은 **관측 상태는 echo-was(관리 평면)가 이미 보유**합니다. 여기서 중복 저장하지 않고 echo-was를 읽습니다.

### 3. 클라우드 Managed DB
- RDS·Cloud SQL 등은 온프레미스처럼 Binlog를 같은 방식으로 읽기 어렵습니다.
- 대신 클라우드가 제공하는 방식(provider-native)을 씁니다. RDS는 DMS·cross-region read replica, Cloud SQL은 자체 replication·export.
- 그래서 1번(직접 Binlog)과 경로가 갈립니다. 하나로 묶지 않습니다.

### 4. 설정·시크릿
- DB에는 비밀값을 넣지 않고, 보관 위치(`secret_ref`)만 둡니다.
- 특정 클라우드 시크릿 서비스에만 두면 failover 시 다른 클라우드에 비밀이 없습니다. 값을 클라우드 간 복제하거나, 특정 클라우드에 묶이지 않은 Vault를 씁니다.
- 비밀이 아닌 일반 설정은 시크릿과 분리해 2번(Git)에 둡니다.

### 5. 비정형 오브젝트 파일
- 클라우드 간 공유는 쉽지만 온프레미스가 문제입니다.
- 온프레미스 디스크·NAS 앞에 **MinIO(S3 호환 저장소)**를 세우면, 온프레미스와 클라우드가 같은 Object Storage로 보입니다.
- 그러면 복제가 한 방식으로 통일됩니다(rclone·mc mirror). 1번 백업 저장소도 같은 인터페이스로 묶입니다.

### 6. 네트워크 라우팅·인프라 권한
- "백업"이라기보다 **IaC**입니다. 원본은 Terraform 코드(Git) + state이고, 손으로 만든 것을 백업하는 게 아니라 코드로 다시 세웁니다.
- IAM 같은 권한은 클라우드마다 1:1 복사가 안 됩니다. 환경별로 다시 표현해야 합니다(환경 격차 매핑). → 추가 설계 필요.

### 7. CDC offset
- 1·3번을 중간부터 다시 시작할 수 있게 하는 메타데이터입니다.
- 소스별 마지막 Binlog 위치(position·GTID)와 Consumer offset을 저장합니다.
- 이 값이 유실되면 처음부터 전체 재동기화(full re-sync)로 떨어집니다. 따라서 offset 자체도 내구 저장하고 백업 카탈로그(10번)와 함께 둡니다.

### 8. DNS·트래픽 입구 상태
- 지금 어느 도메인이 어디로 향하는지, 환경별 traffic_weight(트래픽 분배 비율)가 얼마인지입니다.
- 재해 시 이를 전환해야 하므로, 복구 대상이 아니라 **상시 알고 있어야 하는 상태**입니다.

### 9. 스키마 버전 ↔ 이미지 버전 정합성
- 데이터만 복원하고 앱이 다른 스키마면 깨집니다.
- 백업 시점의 schema version을 image digest와 함께 묶어 Checkpoint에 둡니다.

### 10. 백업 카탈로그
- 무엇을·언제·어디에 백업했는지와 체크섬·크기를 기록합니다.
- 이게 없으면 백업이 있어도 찾지 못하고 검증도 못 합니다. 7번 offset과 함께 둡니다.

### 11. 서비스 종속성 그래프
- 서비스 하나가 쓰는 DB·시크릿·오브젝트·라우트를 묶은 지도입니다.
- 이게 있어야 "서비스를 통째로" 옮길 수 있습니다. (echo-ai-agent의 blueprint 추출과 연결됩니다)

### 12. 정합성 기준점(Checkpoint)
- 한 서비스가 DB를 2개 이상 쓰면, 복구 시 그것들이 같은 시점으로 맞아야 데이터가 어긋나지 않습니다.
- 소스별 offset만으로는 부족하고, "이 묶음은 T 시점 기준"이라는 공통 체크포인트가 필요합니다.

## 5. 아직 정할 것 (판단 항목)

- **RPO·RTO 목표 수치** — Snapshot 주기, Checkpoint 주기, warm standby 여부가 모두 여기서 따라옵니다.
- **백업 Object Storage 최종 선택** — S3 / GCS / MinIO 중 어디에 둘지
- **시크릿 클라우드 간 복제 방식** — 값 미러 vs 중립 Vault (4번)
- **IAM·네트워크 환경 격차 매핑 방식** (6번)
- **schema_version·image_ref 출처** — echo-was DB를 읽을지 자체 보관할지 (9번)
