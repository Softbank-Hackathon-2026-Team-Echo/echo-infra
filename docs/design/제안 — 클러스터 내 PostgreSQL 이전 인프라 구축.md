# 제안 — 클러스터 안 PostgreSQL 이전 인프라를 세워 주세요

- 보내는 사람: 데이터·이전 엔진 담당 (이도현)
- 받는 사람: 인프라 담당 (서동옥)
- 날짜: 2026-11-03
- 근거: [ADR-0004](../adr/[ADR-0004]%20데이터%20이전%20—%20PostgreSQL%20논리%20복제%20+%20PgBouncer%20컷오버.md), [SPEC infra-7](../../specs/infra-7-postgres-logical-replication-cutover.md)

## 한 줄 요약

재난 데모의 핵심인 **데이터 이전(AWS 도쿄 → GCP 서울)**을 실제로 보여주려면, 두 클러스터 안에 **직접 관리하는 PostgreSQL**이 있어야 합니다. 클러스터·레지스트리·진입점은 이미 세워 주셨으니, 이제 그 위에 올라갈 **DB와 둘을 잇는 복제 경로**를 세우는 일을 부탁드립니다. 매니페스트 1차안과 로컬 검증은 제가 준비해 뒀습니다.

---

## 1. 지금 상황 — 무대는 섰는데 주인공이 없습니다

AWS 도쿄 EKS, GCP 서울 GKE, 레지스트리, 고정 진입점(Envoy), 관제탑(echo-was)까지 서 있습니다. 하지만 재난 데모에서 **실제로 "옮겨지는" 데이터**가 아직 없습니다. 아키텍처 문서에도 "도쿄 안 DB 없음"이라고 적혀 있습니다. 지금 상태로는 트래픽은 서울로 넘길 수 있어도, **그 서비스가 쓰는 데이터는 도쿄에 묶여 있어** 도쿄가 죽으면 같이 죽습니다. 이건 재난 복구 데모의 가장 중요한 장면이 비는 것입니다.

그래서 **"데이터를 손실 없이 옮기고, 필요하면 되돌린다"**를 실제로 보여줄 DB 인프라가 필요합니다.

### 확인한 현재 상태 (2026-11-03, 도쿄 계정 읽기 전용 조회 — 아무것도 바꾸지 않음)

| 항목 | 상태 | 의미 |
|---|---|---|
| EKS `echo-dev-eks` | ACTIVE · k8s 1.35 · 노드 2대 Ready(10.50.x) | **바탕 준비됨** |
| 애드온 | `aws-ebs-csi-driver`·vpc-cni·coredns 등 | PVC(디스크) 받을 준비됨 |
| 기본 StorageClass | **`ebs-csi-default-sc`** (ebs.csi.aws.com) + `gp2`(레거시) | 디스크 동적 생성 가능 |
| RDS | **없음** | 매니지드 DB 안 씀(ADR-0004)이 맞게 비어 있음 |
| `echo-data` 네임스페이스 / DB용 PVC / 로드밸런서 | **모두 없음** | **DB·앱은 아직 0 — 이번에 세울 대상** |

즉 바탕(클러스터·노드·EBS CSI·기본 SC)은 다 섰고, **그 위 DB만 비어 있습니다.** 올리기만 하면 되는 상태입니다.

## 2. 왜 이렇게 하려는지 — 결정별 이유

### 왜 RDS/Cloud SQL 이 아니라 클러스터 안 self-managed PostgreSQL 인가 (ADR-0004)

재난 시나리오는 **도쿄 → 서울 cross-cloud 이전**입니다. 매니지드 DB(RDS)는 AWS 안에 갇혀 있어서, GCP 쪽 매니지드(Cloud SQL)로 **논리 복제를 직접 걸기가 까다롭습니다.** 또 무손실 컷오버를 하려면 `wal_level`·복제 슬롯·PgBouncer 전환 타이밍을 **우리가 직접 통제**해야 하는데, RDS는 구현해야 하는 것이 더 많습니다. 
그래서 두 클러스터 안에 똑같은 구조의 Postgres를 직접 띄우는 쪽을 택했습니다. (상세 비교는 ADR-0004)

### 왜 도쿄(A)부터인가

도쿄가 평상시 주인(Primary)입니다. 여기서 데이터가 흘러나가야(publication) 서울이 받습니다(subscription). 출발점이 없으면 아무것도 시작되지 않으니 **도쿄 A를 먼저** 세웁니다.

### 왜 PgBouncer가 꼭 필요한가 — 이게 "무손실"의 핵심입니다

복제는 비동기라 서울은 도쿄보다 항상 몇 줄 뒤처져 있습니다. 이 상태에서 그냥 주인을 바꾸면 **마지막 몇 줄이 사라집니다.** PgBouncer를 앱과 DB 사이에 두면, 컷오버 순간 **쓰기를 아주 잠깐 멈춰** 뒤처진 간격을 0으로 만든 뒤 넘길 수 있습니다. 앱은 접속 주소를 바꾸지 않고, PgBouncer 뒷단만 A→B로 바꿉니다. **이 장치가 없으면 "무손실"이 아닙니다.**

### 왜 cross-cloud 네트워크 경로와 TLS가 필요한가

서울(B)이 도쿄(A)의 Postgres에 **직접 붙어** 변경을 받아야 복제가 됩니다. 두 클라우드 사이 경로가 없으면 복제 자체가 불가능합니다. 그리고 그 길에는 **DB 트래픽(비밀번호·데이터)**이 흐르므로, 암호화(TLS) 없이는 그대로 노출됩니다. 그래서 cross-cloud 경로 + TLS + 접근 허용 목록이 필요합니다.

## 3. 부탁드리는 것 (단계별)

제가 준비한 매니페스트는 `replication/k8s/aws-tokyo/`에 있습니다. 공유 클러스터를 바꾸는 일이라 **apply는 확인하신 뒤 직접** 해주시면 됩니다.

| 단계 | 요청 | 왜 |
|---|---|---|
| **1. 도쿄 A 내부** | `echo-data` 네임스페이스에 Postgres(StatefulSet, `wal_level=logical`) + PgBouncer apply. 비밀번호 k8s Secret은 손으로 생성 | 복제의 출발점. 매니페스트·검증 절차 준비됨 |
| **2. 도쿄 A 외부 노출** | 서울에서 접속할 수 있게 **NLB(또는 사설 경로) + TLS 서버 인증서 + 보안그룹 허용**(소스 = GCP `nat_ip`) | 서울이 도쿄 DB에 붙어야 복제가 흐름 |
| **3. 서울 B 미러** | GKE 서울에 같은 Postgres + 구독(subscription). 비밀은 Secret Manager | 받는 쪽. 여기로 데이터가 흘러들어옴 |

**오늘 논의해야 하는 것:**
- **cross-cloud 연결 방식** — 사설 VPN/피어링 vs 공인 엔드포인트 + TLS. (아키텍처 문서는 VPN을 가정하고, 계약의 `nat_ip`는 공인+허용목록을 시사합니다. 하나로 확정이 필요합니다.)
- **도쿄 A Postgres의 노출 주소와 TLS 인증서** — 인증서의 SAN이 그 주소와 같아야 서울이 `verify-full`로 안전하게 붙습니다. 인증서 발급 주체도 정해야 합니다.
- **복제 유저 비밀의 보관 위치** — AWS Secrets Manager / GCP Secret Manager. (저장소엔 비밀값 0건, NFR-17)

## 4. 이미 검증해 둔 것

막연한 요청이 아니라, 메커니즘은 **로컬에서 실제로 돌려 숫자로 확인**해 뒀습니다(`replication/` PoC).

- ✅ 논리 복제 → 무손실 컷오버 → 되돌리기까지 왕복 동작, **누락 0 · 중복 0**(순번 1~500 연속).
- ✅ 쓰기를 멈추는 시간 **≈0.30초**, 컷오버 시점 복제 지연 **≈0.07초** → **NFR-03(≤1초) 충족**.
- ✅ 서울로 넘겼다가 도쿄로 되돌리는 복귀 시간 **≈0.46초** → **NFR-05(≤60초) 충족**.

즉 "되는지 모르는 걸 해보자"가 아니라, **되는 걸 실제 클러스터로 옮기는 단계**입니다. 도쿄 A용 k8s 매니페스트도 1차안으로 작성해 뒀습니다(trust → scram 인증, docker → StatefulSet+PVC로 전환 완료).

또 매니페스트를 **실제 클러스터 상태에 맞춰 뒀습니다** — 위에서 조회한 기본 StorageClass 이름(`ebs-csi-default-sc`)을 그대로 반영했습니다(기본값이 `gp3`가 아니라 이 이름이라, 안 맞추면 PVC가 Pending 에 걸립니다). 남은 건 **비밀 Secret 생성 + apply** 뿐입니다. 다만 **실제 apply해 끝까지 검증한 것은 아니므로**, 함께 올려 보며 확인하는 절차를 README에 적어 뒀습니다.

## 5. 다 되면 무엇이 가능해지나

- 재난 버튼을 눌렀을 때 **데이터까지** 서울에서 살아나는 장면을 실제로 보여줄 수 있습니다.
- "몇 건이 빠졌나"를 **0으로** 증명하고, 멈춘 시간·복귀 시간을 **측정값으로** 보여줄 수 있습니다(심사 근거 화면과 직결).
- 관제탑(echo-was)의 이전 계획이 복제 지연을 읽어 **안전할 때만 100% 전환**하도록, 데이터 쪽 연결(#7의 DataSyncChecker)을 실제로 붙일 수 있습니다.

## 6. 리스크와 비용

- **EBS 단일 볼륨**: 지금 A는 복제본이 서울(B)뿐입니다. 도쿄 쪽 디스크 장애 자체의 대비는 백업(#14)에서 따로 다룹니다.
- **cross-cloud 트래픽**: 도쿄↔서울 복제는 네트워크 비용과 지연(RTT)이 듭니다. 로컬 숫자(0.3초)는 **실제 cross-cloud에서 다시 재야** 합니다("B 따라잡기"가 RTT만큼 늘 수 있음).
- **NAT 1개(AZ 1a) 약점**: 아키텍처 문서 §6에 적힌 기존 약점이 복제 경로에도 영향을 줄 수 있어 함께 봐야 합니다.
- **이미지 고정**: 1차안은 `postgres:17` 태그라, 동작 확인 뒤 digest로 고정하겠습니다.
