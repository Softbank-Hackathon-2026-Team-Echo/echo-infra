# 온프레미스 DB 백업 및 동기화 파이프라인

> ⚠️ **대체됨 (2026-11-03) — 이 문서는 MySQL/Debezium 전제로 쓴 옛 설계입니다.**
> 앱 DB가 PostgreSQL로 확정되고(이슈 #4) 이전은 **네이티브 논리 복제 + PgBouncer 컷오버**([ADR-0004](<../adr/[ADR-0004] 데이터 이전 — PostgreSQL 논리 복제 + PgBouncer 컷오버.md>)), 백업은 **base backup + 연속 WAL(PITR)**로 바뀌었습니다. 현재 설계는 ADR-0004와 SPEC `infra-7`·`infra-8`·`infra-14`를 보세요. 이 문서는 Postgres 기준으로 재작성 예정입니다.

이 문서는 이번 작업의 전체 그림을 설명합니다.

목표를 한 줄로 말하면, **온프레미스 서버에서 돌아가는 서비스의 데이터를 평소에 클라우드로 조금씩 계속 복사해두고, 온프레미스에 문제가 생기면 클라우드에서 그 서비스를 똑같이 다시 켜는 것**입니다.

여기서 "복구"는 서비스를 다른 환경에서 다시 가동(Failover)하는 것을 뜻합니다. 망가진 DB를 과거로 되돌리는 것이 아닙니다. 자세한 근거는 [ADR-0001](<../adr/[ADR-0001] 데이터 정합성 — 복제 시점이 아니라 복구 기준점으로.md>)에 있습니다.

도식에는 MySQL로 되어 있지만, 고정된 DBMS가 아니라 예시로 MySQL을 쓴 것입니다. (다른 DB도 같은 구조로 동작합니다. 뒤의 "5. 다른 DBMS는?" 참고)

## 0. 용어 정리
- **Binlog (바이너리 로그):** MySQL이 쓰는 "변경 일기장"입니다. 누가 어떤 행을 추가·수정·삭제했는지를 **일어난 순서대로 전부** 적습니다. 우리는 이 일기장을 어깨너머로 읽으며 변경을 따라갑니다.
- **CDC (Change Data Capture):** DB에서 "바뀐 것만" 뽑아내는 일입니다. 위의 Binlog를 읽는 게 바로 CDC입니다.
- **Debezium:** 이 CDC를 대신 해주는 오픈소스입니다. DB의 Binlog를 읽어 변경 이벤트를 만들어 Redis로 보내주고, 우리는 그걸 받아 쓰기만 하면 됩니다. (도입 결정: ADR-0003)
- **Snapshot (스냅샷 / 덤프):** 특정 순간의 DB 전체를 통째로 찍은 "사진 한 장"입니다.
- **offset / GTID:** 일기장을 "몇 번째 줄까지 읽었는지" 가리키는 **북마크**입니다. MySQL에서는 GTID라는 번호가 그 역할을 합니다.
- **Redis Stream:** 변경 메시지를 온프레미스에서 중앙 플랫폼으로 실어나르는 "**컨베이어 벨트**"입니다. 데이터를 보관하진 않고 전달만 합니다.
- **멱등 (Idempotent):** 같은 작업을 **두 번 해도 결과가 같은** 성질입니다. 컨베이어가 같은 메시지를 실수로 두 번 보내도 데이터가 틀어지지 않게 하려고 필요합니다.
- **Checkpoint (체크포인트):** 게임의 "**세이브 포인트**"입니다. "여기로 돌아가면 서비스를 안전하게 다시 켤 수 있다"는 지점을 적어둡니다.
- **Failover (페일오버):** 주 서버가 죽었을 때 예비 환경으로 서비스를 넘기는 것입니다.

## 1. 평상시 — 데이터를 미리미리 옮겨둡니다

**왜 평소에 미리 옮길까요?**

재해가 터진 뒤에 거대한 데이터를 통째로 옮기면 시간이 너무 오래 걸립니다. 그래서 평소에 조금씩 미리 복사해두고, 재해 때는 "거의 다 와 있는" 상태에서 마무리만 합니다.

**어떻게 조금씩 옮길까요?** 두 단계입니다.

1. **처음 한 번:** 전체 사진(Snapshot/덤프)을 떠서 클라우드로 보냅니다. 여기서 기준점이 생깁니다.
2. **그 다음부터:** 바뀐 것만(Binlog) 계속 흘려보내 그 사진 위에 덧칠합니다.

아래가 그 전체 그림입니다. 박스 하나하나를 뒤에서 설명합니다.

![DB 백업 구조도](<DB 백업 구조도 1.png>)

> 이 그림은 **평상시** 흐름입니다. 재해 때 복구는 아래 "2. 재해가 나면"에서 설명합니다.
> 그림의 "Redis Producer #2" 박스는 이제 **Debezium Server**를 가리킵니다(ADR-0003으로 변경). 편집용 도식: [평상시 구조도.drawio](<./평상시 구조도.drawio>)

이제 그림의 화살표를 따라 단계로 봅시다.

1. **온프레미스 환경(Docker)** 안에서 **서비스**가 **DBMS**에 데이터를 씁니다.
2. DBMS는 쓸 때마다 **Binlog(변경 일기)에 자동으로** 기록합니다. (그림의 `binlog = ROW + GTID`. ROW는 바뀐 행을 그대로 적는 방식, GTID는 북마크 번호입니다.) 트리거를 걸어 부하를 주지 않아도 됩니다.
3. 온프레미스에 자동으로 띄운 **Debezium Server(#2)**가 그 Binlog를 읽어 "이런 변경이 있었다"는 메시지로 만듭니다. Debezium은 CDC를 대신 해주는 오픈소스라, 우리가 Binlog 파싱·초기 스냅샷·offset 관리를 직접 짜지 않아도 됩니다(ADR-0003). ("자동 추가" = 이 Debezium 컨테이너를 온프레미스 환경에 우리가 자동으로 띄워준다는 뜻이고, 그림의 "Redis Producer #2" 박스가 바로 이것입니다.)
4. 그 메시지를 **플랫폼(중앙)**의 **Redis Stream**으로 보냅니다(그림의 "데이터 변경점 log 전달 [#1 계약]" 화살표). 흐르는 것은 실제 데이터가 아니라 "변경점 메시지"뿐입니다. Redis Stream은 전달 통로일 뿐, 백업본이 아닙니다.
5. **Redis Consumer(#3)**가 Stream에서 그 메시지를 받아, **대상 환경(클라우드)의 타겟 복제본 DB**에 변경을 그대로 적용합니다. 이때 **멱등하게(PK Upsert)** 적용해서, 같은 메시지가 두 번 와도 안전합니다.
   - 이 복제본은 처음에 덤프로 한 번 깔아둔 뒤, 이 변경 메시지들로 **계속 최신으로 유지**됩니다. 그래서 그림에 "계속 반영되는 최신 사본"이라고 적혀 있습니다.
6. Consumer는 동시에 **메타 저장소(#5)**에 "**처리한 offset**"을 적습니다. 메타 저장소는 카탈로그(무엇을 어디에 백업했나)와 **Checkpoint**(offset + schema + image, 즉 "어디로 복구하면 되는지")를 들고 있습니다.
7. 한편 **DBMS에서 곧바로** 주기적인 Snapshot과 연속 Binlog를 **백업 저장소(#4, Object Storage / MinIO)**에 쌓아둡니다. 이건 복구할 때 쓰는 "재료"입니다.

**정리하면, 변경은 두 갈래로 나갑니다.**

- **① 라이브 갈래:** 타겟 복제본 DB까지 실시간으로 반영됩니다. 재해 때 빠르게 켜기 위함입니다.
- **② 백업 갈래:** 백업 저장소에 Snapshot + Binlog로 차곡차곡 쌓입니다. 복구 재료이자, 복제본까지 잃었을 때의 안전망입니다.

## 2. 재해가 나면 — 클라우드에서 서비스를 다시 켭니다

온프레미스가 죽었다고 합시다(예: 지진으로 서버실이 내려감).

다행히 평상시에 만들어 둔 **타겟 복제본 DB**가 이미 거의 최신입니다. 그래서 복구는 대부분 "그 복제본 위에서 서비스를 켜는 것"입니다.

순서는 이렇습니다.

1. **Checkpoint를 읽습니다.** 어느 지점(C)으로 켤지 정합니다. (세이브 포인트 고르기)
2. **복제본을 그 지점(C)에 맞춥니다.** 복제본이 조금 뒤처져 있으면, 백업 저장소의 Binlog로 마지막 구간만 채워 C까지 올립니다.
3. **서비스를 켭니다.** 이때 아주 중요한 점: 데이터만 맞추면 안 되고, 그 시점의 **앱 버전(image)과 DB 구조(schema)도 함께** 맞춰야 합니다. 안 그러면 새 앱이 옛 데이터를, 또는 그 반대를 만나 깨집니다. (이 두 값은 Checkpoint에 같이 적혀 있습니다.)
4. **검증합니다.** 다 켜고 나서 체크섬·행수를 비교해 "제대로 복구됐는지" 확인합니다.

> 복제본까지 잃은 경우(복제본이 오염됐거나 그 환경도 죽은 경우)에는, 백업 저장소의 **Snapshot을 통째로 올린 뒤 Binlog를 C까지 재적용(replay)**해 복제본을 처음부터 다시 만듭니다. 위 2단계의 "큰 버전"인 셈입니다.

![재해 시나리오 구조도](<재해 시나리오 구조도.png>)

이것이 Failover입니다. 다시 강조하면, **과거로 되돌리는 것이 아니라 "최신 상태로 다른 환경에서 다시 켜는 것"**입니다.

> 이 재해 흐름의 편집용 도식: [재해 시나리오 구조도.drawio](<./재해 시나리오 구조도.drawio>) (draw.io로 열어 수정한 뒤 png로 export하면 됩니다.)

## 3. 왜 이렇게까지 하나요? (설계 이유)

**Q. 왜 실시간으로 똑같이(동기 복제) 맞추지 않나요?**
동기로 묶으면 원본이 복제 대상을 매번 기다리느라 느려지고, 복제 대상이 죽으면 원본까지 멈춥니다. 지키려고 만든 백업이 원본을 망치면 안 됩니다. 그래서 비동기로, 조금 뒤처지는 것을 허용하며 흘려보냅니다.

**Q. 왜 Snapshot(사진)만으론 안 되나요?**
사진과 사진 사이에 바뀐 데이터가 유실됩니다. 그래서 사진 + 그 뒤의 Binlog(일기)를 같이 둡니다. 복구 = 사진 적재 + 일기 덧칠입니다.

**Q. 왜 Checkpoint가 필요한가요?**
한 서비스가 DB를 여러 개 쓰면, 복구할 때 그것들이 "같은 시점"으로 맞아야 데이터가 어긋나지 않습니다. Checkpoint는 그 "같은 시점"을 적어두는 세이브 포인트입니다.

**Q. 왜 백업을 DB가 아니라 Object Storage(MinIO/S3)에 두나요?**
사진·일기처럼 큰 파일 덩어리는 DB보다 Object Storage가 더 싸고 적합합니다. 온프레미스에는 MinIO(S3처럼 쓰는 저장소)를 세워 클라우드와 같은 방식으로 다룹니다.

## 4. 어떤 박스가 어떤 작업(이슈)인가요?

| 요소 | 이슈 | 하는 일 |
| --- | --- | --- |
| 이벤트 포맷(Debezium) | #1 | Debezium 이벤트 포맷을 채택하고, 쓰는 필드를 내부 형태로 고정합니다 |
| Debezium Server | #2 | 온프레미스 DB의 Binlog를 읽어 Redis Stream으로 변경 이벤트를 보냅니다(캡처) |
| Redis Stream + Consumer | #3 | 메시지를 받아 복제본에 멱등하게 적용합니다 |
| 백업 저장소 | #4 | Snapshot + Binlog를 Object Storage에 쌓아둡니다 |
| 메타 저장소 | #5 | 카탈로그(무엇을 어디에 백업했나) + Checkpoint(어디로 복구하나) |
| 대상 환경 복구 | #6 | Checkpoint와 백업으로 서비스를 다시 켭니다(Failover) |
| 복구 측 어댑터 | #7 | DB별 복구·promote 차이를 공통 인터페이스로 가둡니다 (캡처는 Debezium) |

## 5. 다른 DBMS는 어떻게 하나요?

MySQL은 "첫 번째 예시"일 뿐입니다. 사실 모든 주요 DB가 "변경 일기장 + 북마크"를 갖고 있어서, 이름만 다르지 구조는 같습니다.

```
   MySQL      : Binlog(ROW)        북마크 = GTID
   PostgreSQL : WAL(logical)       북마크 = LSN
   Oracle     : redo log / LogMiner 북마크 = SCN
   SQL Server : transaction log     북마크 = LSN
```

가운데 흐름(메시지 · Redis · Consumer · 백업 · 메타 · 복구)은 DB 종류와 상관없이 그대로 씁니다. DB마다 다른 부분은 **양 끝 두 곳뿐**입니다.

- **변경 읽기(캡처):** Debezium이 DB별 커넥터로 해결합니다. 우리가 DB마다 새로 짜지 않고, 커넥터 설정만 바꿉니다.
- **그 지점까지 맞춰서 켜기(복구):** DB별 복구 어댑터(#7) 파일 하나만 더합니다.

> 캡처는 **Debezium Server로 하기로 정했습니다(ADR-0003).** Binlog 파싱·초기 스냅샷·offset·멀티 DBMS를 Debezium이 가져가고, 우리는 멱등 적용·백업·Checkpoint·Failover에 집중합니다. CDC 커넥터가 없는 DB는 주기적 덤프로 폴백합니다.

## 이 작업에 포함되지 않는 것

이 문서의 범위 밖이라 그림에도 넣지 않았습니다.

- **Managed DB(RDS·Cloud SQL) 경로** — 클라우드가 대신 운영하는 DB는 방식이 달라 별도 어댑터로 다룹니다.
- **Git · Argo CD 배포 정의 트랙** — 데이터가 아니라 "어떤 앱을 어떻게 띄우나"를 다루는 평행한 작업입니다. (데이터 정의 문서 2번)
- **트래픽 전환(무중단 이전 엔진)** — 사용자 트래픽을 옮기는 부분은 이전 엔진 쪽 트랙입니다.
- **랜섬웨어 과거 복원** — 과거의 깨끗한 시점으로 되돌리는 복구는 성격이 달라 [ADR-0002](<../adr/[ADR-0002] 논리적 재해 복원 — 과거 clean 지점 Restore를 다룰 것인가.md>)에서 따로 다룹니다.
