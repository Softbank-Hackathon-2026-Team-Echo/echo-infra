# 롤백 절차서 — GCP 서울(B) → AWS 도쿄(A)

- 대상: 이전 엔진을 운영하는 사람(당직자·데모 진행자)
- 근거: [SPEC infra-8](../../specs/infra-8-rollback-reverse-replication.md), [ADR-0004](../adr/[ADR-0004]%20데이터%20이전%20—%20PostgreSQL%20논리%20복제%20+%20PgBouncer%20컷오버.md)
- 선행: #7 컷오버(A→B)가 끝나 **현재 primary 가 B** 인 상태입니다.

이 문서는 컷오버로 서울(B)에 넘어간 쓰기를 다시 도쿄(A)로 **안전하게 되돌리는** 방법을 적습니다. 로컬 PoC 는 `replication/scripts/{reverse,rollback}.sh` 로 그대로 재현됩니다.

---

## 용어 정리

- **컷오버(Cutover)**: 쓰기를 받는 주인(primary)을 한 DB 에서 다른 DB 로 넘기는 일입니다. 여기서는 A→B.
- **롤백(Rollback)**: 넘겼던 주인을 되돌리는 일입니다. 여기서는 B→A.
- **역방향 복제(Reverse replication)**: 평소 B 의 변경을 A 로 계속 흘려보내, A 를 **언제든 돌아갈 수 있는 예비(warm standby)** 로 유지하는 것입니다. 롤백이 빠르려면 이게 먼저 켜져 있어야 합니다.
- **재동기화(Resync)**: A 가 B 보다 뒤처져 있을 때(컷오버 뒤 B 가 더 썼으므로), A 를 비우고 B 를 통째로 다시 받아 **B 와 똑같이 맞추는** 일입니다.
- **PgBouncer**: 앱과 DB 사이의 연결 중개자입니다. 롤백은 접속 문자열을 바꾸는 게 아니라, PgBouncer 의 뒷단(backend)을 B→A 로 **바꿔 끼우는** 것으로 이뤄집니다.
- **시퀀스 맞춤(Sequence align)**: 논리 복제는 `id` 자동 번호(시퀀스)를 옮기지 않습니다. 그래서 되돌릴 때 A 의 시퀀스를 최신으로 올려 두어야 **새 행의 `id` 충돌**이 없습니다.
- **NFR-05**: 장애 시 **60초 안에 A 로 100% 복귀**해야 한다는 요구치입니다.

---

## 두 가지 롤백을 구분합니다

| 상황 | 무엇이 다른가 | 데이터 손실 |
|---|---|---|
| **계획적 롤백** | B 가 멀쩡합니다. 쓰기를 잠깐 멈추고(PAUSE) A 가 따라잡은 뒤 넘깁니다. | **없음**(무손실). 이 문서의 기본 절차 |
| **재난 롤백** | B 가 급사해 역방향 복제가 끊깁니다. | 마지막 몇 초가 빠질 수 있음(RPO>0). A 복구·재동기화가 선행 |

평상시·데모에서는 **계획적 롤백**을 씁니다. 아래 절차는 계획적 롤백 기준입니다.

---

## 0. 사전 조건 — 역방향 복제부터 켭니다 (reverse.sh)

컷오버 직후 **A 를 예비로 되살려 둡니다.** 이걸 미리 해 두어야 롤백이 빠릅니다.

1. 정방향 객체를 정리합니다(B 의 구독, A 의 발행 제거).
2. B 에 역방향 발행 `pub_rev` 를 만듭니다.
3. **A 를 비우고(TRUNCATE) B 를 `copy_data=true` 로 다시 받습니다**(재동기화). A 가 B 의 복제본이 됩니다.
4. 초기 복사가 끝났는지 구독 상태가 `r`(ready)인지로 확인합니다.

> ✅ 확인 포인트: `reverse.sh` 가 "역방향 복제 B→A 가동" 을 출력하고, 이후 B 에 쓰면 A 의 `max(n)` 이 따라 오릅니다.

---

## 1. 계획적 롤백 절차 (rollback.sh)

컷오버(#7)의 **거울상**입니다. 방향만 B→A 로 바꿉니다.

| 단계 | 하는 일 | 확인 포인트 |
|---|---|---|
| ① PAUSE | PgBouncer 가 B 로의 쓰기를 멈추고 진행 중 트랜잭션을 비웁니다. | 앱 쓰기가 잠깐 대기 상태가 됩니다. |
| ② A 따라잡기 | A 가 B 의 `max(n)` 까지 받을 때까지 기다립니다. | 보통 1초 안. 길어지면 역방향 복제 지연을 의심합니다. |
| ③ 시퀀스 맞춤 | A 의 `id` 시퀀스를 `max(id)+1000` 으로 올립니다. | 이후 새 행 `id` 충돌 없음. |
| ④ 구독 중지 | A 가 B 로부터 더 받지 않게 `sub_rev` 를 DISABLE 합니다. | — |
| ⑤ repoint | PgBouncer 뒷단을 B→A 로 바꾸고 RELOAD 합니다. | `pgbouncer.ini` 의 `host` 가 `pg_a`. |
| ⑥ RESUME | 쓰기가 A 로 갑니다. **①~⑥ 구간이 복귀 시간**입니다. | 앱 쓰기가 A 에서 이어집니다. |

> ✅ 완료 확인: `rollback.sh` 가 **복귀 시간**을 출력하고 "이제 primary = A" 라고 알립니다.

## 2. 복귀 후 검증 (Must)

```bash
bash scripts/verify.sh pg_a
```

- **누락 0 · 중복 0** 이어야 합니다(순번 `n` 이 1..최댓값까지 빠짐·겹침 없이 연속).
- 로컬 PoC 왕복(A→B→A) 결과: **211행, n 1~211 연속, 누락 0·중복 0**, 복귀 시간 **≈0.46s**(NFR-05 ≤60s 충족).

## 3. 복구 판단 — 언제 되돌리나

- **계획적 롤백**: A 환경이 정상으로 돌아왔는지 **헬스체크 API 폴링**으로 확인한 뒤 사람이 버튼을 누릅니다(회의 11/2 결정).
- **자동 롤백(Should)**: 전환 뒤 **오류율이 문턱을 넘으면** 자동으로 롤백을 겁니다. 판정 지표·발생기는 측정·관측(#9·#10)과 붙입니다. (실제 연결 단계의 과제)

## 4. 재난 롤백 (B 급사)

B 가 갑자기 죽으면 PAUSE 로 깨끗이 멈출 수 없습니다.

1. B 불능을 헬스체크로 감지합니다.
2. A 는 역방향 복제로 **직전까지 따라와 있던 예비**이므로, PgBouncer 를 A 로 repoint 하고 RESUME 합니다.
3. 이때 **마지막 몇 초의 쓰기가 빠질 수 있습니다**(RPO>0). 손실 구간은 측정·기록에 남깁니다.
4. B 가 복구되면 다시 **재동기화(reverse.sh)** 부터 시작합니다.

## 5. 원본 장애 승격 (A 급사, 실제 클러스터) — 인프라 12.3

도쿄 A 가 쓰기 담당인데 A 가 죽은 경우입니다(재난 긴급 이전의 기본 상황). `cutover.sh` 는 A 를 PAUSE 하고 A 의 복제 상태를 읽어야 해서 쓸 수 없습니다. 대신 **B 만으로 쓰기 담당을 B 로 올립니다.**

```bash
ALLOW_PROMOTE=true PLAN_ID=<긴급 이전 계획 id> B_HOST=<B LB IP> replication/k8s/scripts/cutover.sh
#  → A 에 닿지 않으면(3회 시도) promote.sh 로 넘어갑니다. 직접 promote.sh 를 돌려도 됩니다.
```

1. **A 에 닿는지 먼저 봅니다.** 닿으면 승격하지 않습니다(종료 1). A 가 살아 있는데 B 를 올리면 쓰기 담당이 둘이 되어 데이터가 갈라집니다. 이때는 정상 `cutover.sh` 를 씁니다.
2. B PgBouncer PAUSE → B 시퀀스 맞춤 → B `echo_sub` DISABLE → B PgBouncer 백엔드를 `echo-pg`(B 자신)로 → RESUME.
3. 결과 표에 `kind=CUTOVER, mode=PROMOTE` 와 `rpo_estimate_ms` 를 남깁니다. 이 값은 **B 가 A 에서 마지막으로 받은 시각(없으면 장부의 마지막 쓰기 시각)부터 승격 시작까지의 폭**입니다. A 가 죽은 뒤에는 A 에 쓸 수 없으므로 실제로 잃은 범위는 이 값 이하입니다(상한). 쓰기가 드문 때는 크게 나옵니다.
4. 승격 직후의 장부 대조(누락·중복)는 **B 안에서만** 셉니다. A 에만 있던 행은 이 시점에 보이지 않고, 6절 다시 맞추기에서 개수로 나옵니다.
5. 역방향 구독은 만들지 않습니다(A 가 죽어 있음). 이 상태에서는 `rollback.sh` 가 `PARTIAL` 로 거부합니다 — 먼저 6절을 합니다.

## 6. A 다시 맞추기 (승격 뒤 A 가 살아났을 때) — 인프라 12.3

사람이 상태를 보고 돌립니다(자동으로 돌리지 않습니다).

```bash
B_HOST=<B LB IP> replication/k8s/scripts/resync-a.sh
```

1. A PgBouncer 백엔드를 B 로 바꿉니다(도쿄 앱이 쓰더라도 B 로 가게).
2. **A 에만 남은 장부 행**(승격 전에 B 로 복제되지 못한 쓰기)의 개수와 `n` 목록을 출력합니다. 이 행들은 다음 단계에서 지워집니다 — 손실로 기록해 두세요.
3. B 의 옛 구독 `echo_sub` 를 지웁니다(A 에 남은 슬롯도 함께 지워져 A 의 WAL 이 쌓이지 않습니다).
4. A 의 복제 대상 표(`echo_pub` 의 표 전부)를 비우고, A 가 B 를 구독합니다(`echo_sub_rev`, `copy_data = true`). 초기 복사가 끝날 때까지 기다립니다(최대 60초, 넘으면 종료 2).
5. 끝나면 **정상 컷오버 뒤와 같은 상태**(B 쓰기 담당, A 사본)입니다. A 로 돌아가려면 1절 `rollback.sh` 를 씁니다. 그 롤백의 장부 대조에 2번에서 지운 행이 **누락**으로 나옵니다.

로컬 시험(`replication/k8s/scripts/tests/run.sh` 13~18): A 에만 쓴 행 1건을 만든 뒤 A 를 멈추고 승격 → B 쓰기 → A 재기동 → 다시 맞추기(1건 보고) → 롤백(누락 1) 까지 확인했습니다.

## 체크리스트

- [ ] 롤백 전 역방향 복제가 켜져 있고 `sub_rev` 상태가 `r` 인가
- [ ] 복귀 시간이 60초 안인가 (NFR-05)
- [ ] 복귀 후 `verify.sh pg_a` 가 누락 0·중복 0 인가
- [ ] `pgbouncer.ini` 의 `host` 가 `pg_a` 로 바뀌었는가
- [ ] (재난 시) 손실 구간(RPO)을 기록했는가
- [ ] (A 급사 승격 시) A 에 닿지 않는 것을 확인했는가 · `rpo_estimate_ms` 와 다시 맞추기에서 나온 A 전용 행 수를 기록했는가

## 실제 배포로 갈 때 바뀌는 것

- `pg_a`·`pg_b` → 각 클러스터 안 self-managed PostgreSQL. repoint 는 파일 수정이 아니라 컷오버 API·설정 반영.
- 수동 버튼 → 관제탑(echo-was) UI·API(#6). 헬스체크·오류율은 #9·#10 지표로.
- 복귀 시간·손실 구간을 측정·관측에 자동 기록.
