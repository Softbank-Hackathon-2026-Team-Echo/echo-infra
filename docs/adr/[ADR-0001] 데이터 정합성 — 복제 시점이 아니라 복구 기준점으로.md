## 1. Context (배경)

본 문서는 BCDR 플랫폼이 무중단 데이터 마이그레이션 및 복구 수행 시, 데이터 정합성을 무엇으로, 어디서 보장할 것인가에 대한 기술적 기준을 정의한다.

여기서 '복구'는 장애가 난 서비스를 대상 환경에서 다시 가동(Service Recovery / Failover)하는 것을 뜻한다. 가장 최신의 일관된 데이터 위에서 서비스를 올리는 것이지, 살아 있는 DB를 과거 시점으로 되돌리는 원상복구(Restore / PITR)가 아니다.

플랫폼은 Base Snapshot 적재 후 트랜젝션 로그(Binlog) 기반 CDC(Change Data Capture)를 순차적으로 재해석(Replay)하여 데이터를 복구한다. 이때 복구 처리 시점의 정확한 추적과 데이터 유실·중복 방지를 위해 GTID(Global Transaction ID)를 핵심 오프셋 기준으로 활용한다.

### 요구사항 정의

완벽한 데이터 정합성을 확보하기 위해 다음 3가지 요구사항이 반드시 충족되어야 한다.

1. 멱등성(Idempotency) 보장: 동일한 트랜잭션 메시지가 재전송(Replay)되어도 타겟 DB의 최종 상태는 동일해야 한다.

2. 스키마 및 이미지 버저닝 연동: 데이터 저장 시 해당 시점의 Schema Version과 Container Image 정보가 함께 저장·동기화되어 데이터 포맷 불일치를 방지해야 한다.

3. 다중 DB 간 시점 동기화(Point-in-time Consistency): 단일 서비스가 2개 이상의 DB를 사용할 경우, 복구 시 두 DB가 동일한 GTID/트랜잭션 시점으로 정렬되어야 한다.

### 플랫폼이 보장해야 하는 정합성은 세 가지이다

| 계층 | 대상 | 정합성 정의 | 부재 시 발생 문제 (Failure Mode) |
| --- | --- | --- | --- |
| L1. 단일 소스 내부 | 단일 DB | 원자성(Atomicity) 보장 (All or Nothing) | 반쪽 트랜잭션 발생 (예: 주문 DB 레코드는 존재하나 결제 레코드가 누락) |
| L2. 소스 간 시점 | 다중 DB & Object Storage | 동일 서비스 내 이종 저장소 간 시점 일치 (Point-in-time Consistency) | 저장소 간 복구 시점 불일치로 인한 참조 무결성 파괴 |
| L3. 데이터와 코드 간 | 데이터 & 서비스 실행 환경 | 데이터 복구 시점과 Schema / Container Image 버전의 일치 | 이전 데이터 포맷과 신규 애플리케이션 간 호환성 상실로 시스템 충돌 |

### 제약 조건 및 trade off

가장 단순한 해결책은 "강한 정합성(Strong Consistency)을 위한 동기 복제(Synchronous Replication) 및 분산 트랜잭션(2PC)"을 도입하는 것이지만, 본 BCDR 플랫폼 환경에서는 다음의 치명적인 제약으로 인해 적용이 불가능하다.

1. 원본 성능 저하 방지 (Primary Performance Overhead):

원본(온프레미스)과 복제 대상(클라우드) 간 이종 인프라 네트워크 RTT(Round Trip Time)로 인해, 동기 복제 적용 시 원본 쓰기(Write) 레이턴시가 수평 상승한다.

복제 환경 장애 시 원본 시스템의 쓰기 작업까지 블로킹(Blocking)되거나 중단될 수 있다.
주 시스템의 가용성을 보호하기 위해 도입한 BCDR이 오히려 원본 가용성을 훼손하는 모순을 방지해야 한다.

2. 이종 데이터 저장소 간 분산 트랜잭션 제약 (Heterogeneous Storage Limit):

온프레미스 MySQL, 클라우드 Managed DB, Object Storage를 통틀어 2PC(Two-Phase Commit)를 수행할 공통 인프라 레이어가 부재한다.

재해 상황에서 DB 동기화를 조율하는 코디네이터(Coordinator) 노드에 문제가 생기는 경우,
코디네이터 노드가 동기화 정보를 주기까지 대기하는 모든 참가자(Participant)가 대기 상태(Blocking)로 고립되는 최악의 장애 모드가 발생한다.

그래서 정합성을 **복제 단계에서 강제하지 않는 쪽**으로 방향을 잡는다.

## 2. Decision (결정)

이 플랫폼의 정합성 전략은 아래 한 문장으로 요약된다.

> **정합성은 복제 시점이 아니라 복구 시점에, 소스별이 아니라 서비스 단위 기준점(Consistency Checkpoint)으로 맞춘다.**

복제 과정에서 모든 저장소를 실시간으로 동일하게 맞추려 하지 않는다. 대신 복제는 비동기로 느슨하게 흘려보내고, "언제든 서비스를 올릴 수 있는 일관된 지점"을 주기적으로 만들어 둔다. 복구가 필요한 순간에는 대상 환경의 복제본을 그 지점까지 맞춘 뒤, 그 위에서 서비스를 다시 가동하여 정합성을 확보한다.

### 1. 복제는 비동기 CDC로 흘린다

동기 복제(Synchronous Replication)를 사용하지 않는다. 각 저장소는 자신의 속도에 맞춰 변경분을 흘려보낸다. 온프레미스는 Binlog 기반 CDC로, Managed DB는 클라우드가 제공하는 자체 기능으로 캡처한다. 원본은 복제 대상의 처리 완료를 기다리지 않으므로, 복제 대상이 느려지거나 장애가 나더라도 원본의 쓰기 성능은 영향을 받지 않는다.

다만 이 방식은 복제 대상이 원본보다 일정 시간 뒤처지는 복제 지연(Replication Lag)을 전제로 한다. 이 지연의 폭이 곧 RPO(복구 시 허용되는 데이터 유실 범위)가 된다. 따라서 목표는 지연을 0으로 만드는 것이 아니라, 합의된 RPO 목표 안으로 지연을 가두는 것이다.

### 2. 전달 보장은 at-least-once + 멱등성(Idempotency)으로 한다

분산 환경에서 정확히 한 번 전달(Exactly-once Delivery)을 보장하는 것은 사실상 불가능에 가깝고 비용도 크다. 그래서 다음 두 가지를 조합해 동일한 효과를 저렴하게 얻는다.

- **순서 키 부여:** 모든 변경 이벤트에 GTID 또는 Offset을 붙여, "어디까지 처리했는가"를 추적한다.
- **멱등 적용:** 동일한 이벤트가 두 번 적용되어도 결과가 같도록 PK 기준 Upsert로 반영하고, 이미 처리한 Offset보다 과거의 이벤트는 무시한다.

이렇게 하면 at-least-once(최소 한 번은 전달되며, 중복이 발생할 수 있는 방식) 환경에서 중복 메시지가 들어와도 최종 상태가 틀어지지 않는다. 또한 메시지를 놓치더라도 마지막으로 처리한 Offset 지점부터 다시 받으면 되므로, 한 번의 유실이 전체 장애로 번지지 않는다.

### 3. 정합성 기준점은 서비스 단위로 묶는다

저장소별 Offset만으로는 "여러 저장소가 과연 같은 시점인가"를 알 수 없다. 그래서 하나의 서비스가 사용하는 모든 저장소를 한데 묶는 기준점(Checkpoint)을 둔다. 기준점은 아래와 같이 각 저장소의 위치를 한 번에 가리키는 묶음이다.

```
checkpoint C  (서비스 shop-api, 시각 T)
├─ db-main        : GTID ...:1-10452
├─ db-orders      : GTID ...:1-88301
├─ objects        : version marker v-2026-11-02T03:12:00Z
├─ schema_version : 0007
└─ image_ref      : repo@sha256:9f2c...
```

복구 시에는 서비스가 쓰는 각 저장소를 기준점 C가 가리키는 지점까지 맞춘 뒤, 그 일관된 상태 위에서 서비스를 가동한다. 특정 저장소만 앞서가고 나머지는 뒤처진 상태로 서비스를 올리지 않는다.

**기준점은 서비스를 멈추지 않고 찍는다.**

애플리케이션을 잠시 멈춰(Quiesce) 모든 저장소의 완벽히 동일한 순간을 포착하는 방식(Application-consistent Snapshot)은 사용하지 않는다. 무중단이라는 플랫폼의 목표에 정면으로 어긋나기 때문이다. 대신 주기적으로 각 저장소의 현재 Offset을 한 번에 읽어 기록하는 방식(Crash-consistent)을 택한다. 이 경우 저장소 간 시점이 아주 짧은 구간만큼 어긋날 수 있으나, 그 지점은 언제든 재현과 복구가 가능하다. 이는 DB가 갑작스러운 전원 차단 후 재기동될 때 보장받는 수준의 일관성과 동일하다.

### 4. 기준점에 Schema·Image 버전을 함께 묶는다

기준점 C는 데이터의 Offset뿐 아니라, 그 시점의 Schema Version과 Image Reference(image_ref)를 함께 포함한다.

서비스를 기준점 C가 가리키는 데이터 위에서 가동한다면, 애플리케이션 역시 그 시점의 스키마와 이미지로 함께 올려야 한다. 그렇지 않으면 코드 버전과 데이터 포맷이 어긋나(새 코드가 옛 데이터를 만나거나 그 반대로) 시스템이 깨진다. 이때 이미지는 값이 바뀔 수 있는 Tag가 아니라, 내용으로 고정되는 Digest(image_repository@image_digest)로 지정한다. 이는 echo-was와 공유하는 규칙이며, "그 시점에 무엇이 떠 있었는지"가 Digest에 고정되어 있어야 기준점을 정확히 재현할 수 있기 때문이다.

### 5. 복구는 검증까지가 한 세트다

복구가 "되었다고 가정"하는 것을 신뢰하지 않는다. 기준점마다 복구 결과를 확인할 수단을 함께 남긴다.

- **백업 카탈로그:** 무엇을, 언제, 어디에 저장했는지를 체크섬·크기·기준점 C와 함께 기록한다.
- **복구 후 대조:** 복구가 끝나면 체크섬과 레코드 수를 대조해, 기준점이 가리키는 상태대로 복구되었는지 검증한다.

검증을 통과하지 못한 기준점은 복구 대상에서 제외한다.

### 대안 검토

채택한 방식(E)에 이르기까지 검토한 대안과 기각 사유는 다음과 같다.

| 안 | 방식 | 평가 |
| --- | --- | --- |
| A | 동기 복제 기반 강한 정합성 | 원본이 복제 대상에 묶여 쓰기 지연과 동반 장애가 발생한다. **기각** |
| B | Exactly-once 전송 | 분산 환경에서 사실상 불가능하며 비용이 크다. 멱등성으로 동일한 효과를 낸다. **기각** |
| C | 2PC 기반 소스 간 원자적 기준점 | 이종 저장소를 묶을 공통 기반이 없고, 코디네이터 장애 시 블로킹된다. 재해 상황에 치명적이다. **기각** |
| D | 소스별 독립 복구 (기준점 없음) | 다중 소스 서비스에서 복구 후 저장소 간 시점이 어긋난다. **기각** |
| E | 서비스 단위 느슨한 기준점 + 멱등 적용 | 원본을 건드리지 않고, 유실을 놓쳐도 안전하며, 복구 결과가 일관된다. **채택** |

### 저장소 종류가 달라도 인터페이스는 하나다

저장소 종류마다 복제 메커니즘은 다르다. 온프레미스 DB는 Binlog, Managed DB는 DMS/Replica, Object Storage는 버전 기반 복제(Versioned Replication)를 사용한다. 그러나 플랫폼이 각 저장소를 다루는 인터페이스는 `현재 Offset 읽기`와 `기준점 C까지 맞춰 기동(promote to C)` 두 가지로 통일한다. 종류별 구현 차이는 각 저장소 어댑터 내부에 캡슐화하여, 새 저장소가 추가되어도 상위 로직은 바뀌지 않도록 한다.

### 이번 결정에서 다루지 않는 것

- **RPO·RTO 수치:** 별도 판단 항목이다. 본 ADR은 정합성 모델만 정의하며, 구체적 목표 수치는 추후 확정한다.
- **warm standby 도입 여부:** RPO 수치가 정해지면 그에 따라 결정한다.
- **다중 소스 기준점의 데모 범위:** 데모는 단일 DB 서비스부터 시작하는 것이 현실적이다.
- **Object Storage·Secret의 기준점 통합 수준.**
- **논리적 재해(랜섬웨어·데이터 오염 등) 대응을 위한 과거 clean 지점으로의 Restore:** 본 ADR의 복구는 최신 일관 지점으로의 서비스 재가동(Failover)에 한정한다. 오염 이전의 과거 시점으로 되돌리는 Restore는 성격이 전혀 다르므로, 별도 ADR(ADR-0002 예정)에서 다룬다.

## 3. Consequences (결과 및 영향)

### 🟢 장점

- **원본 성능을 보호한다.** 비동기 복제이므로, 복제 대상이 멀리 있거나 장애가 나더라도 원본의 쓰기 성능과 가용성은 그대로 유지된다.
- **복구 재개가 안전하고 저렴하다.** Offset과 멱등 적용 덕분에, 메시지를 놓쳐도 다시 받으면 되고 중복이 들어와도 최종 상태가 틀어지지 않는다.
- **복구 결과가 일관된다.** 서비스가 사용하는 모든 저장소를 하나의 기준점으로 맞춰 올리므로, 저장소 간 시점 불일치가 발생하지 않는다.
- **데이터와 실행 환경이 함께 복구된다.** 기준점이 Schema Version과 Image를 함께 포함하므로, "데이터만 맞고 코드 버전이 어긋나는" 사고를 원천 차단한다.
- **저장소가 늘어도 구조가 단순하다.** 종류별 차이를 어댑터 내부에 가두므로, 상위에서 보는 인터페이스는 하나로 유지된다.
- **복구를 신뢰할 수 있다.** 카탈로그와 체크섬으로 결과를 검증하기 때문에, "복구했는데 사실 깨져 있었다"를 방지한다.

### 🔴 단점 / 개선안

- **RPO가 0이 아니다.** 재해 발생 직전의 수 초~수 분 데이터는 유실될 수 있다. 따라서 허용 유실 범위를 수치로 합의해야 하며, 더 낮은 RPO가 필요한 핵심 저장소는 warm standby를 별도로 두어야 한다.
- **기준점은 '동일 순간'이 아니라 '근접 시점'이다.** 저장소 간 강한 불변식(예: A DB의 주문과 B DB의 결제가 항상 1:1로 존재)을 요구하는 서비스는 짧은 불일치 구간에서 깨질 수 있다. 이런 서비스는 저장소를 하나로 합치거나 별도 정책으로 다뤄야 한다.
- **멱등성을 저장소마다 보장해야 한다.** Upsert 키나 중복 제거(Dedup) 키 설계가 틀리면 중복이나 유실이 발생한다. 새 저장소를 추가할 때마다 이 부분을 검증하는 과정이 필요하다.
- **기준점·Offset·카탈로그 자체가 또 하나의 핵심 상태다.** 이 메타데이터가 정합성의 기준(Single Source)이 되므로, 이것들 역시 복제·백업 대상이다. 이 정보가 유실되면 데이터가 멀쩡해도 "어느 시점으로 되감아야 하는지"를 알 수 없게 된다.
- **Managed DB는 복제본 승격(Promote) 방식을 provider마다 다시 구현해야 한다.** "기준점까지 맞춰 기동"이 완전히 공통일 수는 없다. 예를 들어 RDS와 Cloud SQL은 복제본을 승격하고 최신 지점으로 맞추는 절차가 서로 다르다.
- **복제본을 최신 일관 지점까지 맞추는 수단이 저장소마다 다르다.** Failover는 임의의 과거 시점이 아니라 '최신 일관 지점' 하나만 있으면 된다. 다만 그 지점까지 복제본을 맞추는 방법은 저장소마다 달라서, 온프레 DB는 Binlog를 이어 적용하면 되지만 일부 Managed/Object Storage는 스냅샷 단위라 기준점 주기를 그 스냅샷 간격에 맞춰야 한다.

- [MySQL GTID 기반 복제][mysql-gtid] — 복제 지점을 전역 트랜잭션 번호로 끊는 방식의 근거다. 기준점의 DB Offset이 바로 GTID다.

- [Redis Streams Consumer Groups][redis-streams] — last-delivered-id와 at-least-once 전달 보장. Offset 추적과 멱등 적용이 필요한 근거다.
