## 1. Context (배경)

### 지금 상태 (2026-11-08 운영 확인, 읽기 전용)

복제는 세 곳에 있지만, 과거 시점으로 되돌릴 수 있는 백업은 없습니다.

| 구분 | 확인 결과 |
|---|---|
| 실시간 복제 | 도쿄 A → 서울 B 논리 복제 `streaming`. 서울 B → 온프레 EC2 `gcpcopy`, 온프레 EC2 → GCP B2·AWS B2 (#134 점검) |
| 백업 작업 | 세 클러스터(EKS, 관제 GKE, 고객 GKE) 모두 CronJob 0, VolumeSnapshot 0 |
| 디스크 스냅샷 | GCP 스냅샷·스냅샷 일정 0, EBS 스냅샷 0, AWS Backup 계획 0, DLM 정책 0 |
| PITR(#14) | SPEC 초안(`specs/infra-14-backup-base-wal-pitr.md`)만 있고 구현 코드 없음 |
| 관제탑 DB | `echo-was/data-echo-db-0` PVC 하나. 복제본·백업 모두 없음 |
| Terraform state | 버킷 버전 관리 켜짐(GCS 확인, S3 는 bootstrap 코드 기준) |

### 복제가 백업이 아닌 이유

발행이 `FOR ALL TABLES` 기본값이라 INSERT·UPDATE·DELETE·TRUNCATE 가 모두 사본으로 넘어갑니다. 원본에서 잘못 지우거나 덮어쓰면 몇 초 안에 B·온프레 사본도 같이 바뀝니다. 복제는 "지금 데이터를 다른 곳에서 살리는" 수단이고, "과거 데이터로 되돌리는" 수단이 아닙니다.

| 재해 | 복제로 막나 | 백업으로 막나 |
|---|---|---|
| 리전·클라우드 장애 | 막습니다 (리허설 실측 있음) | 느리지만 막습니다 |
| 디스크 고장 | 고객 DB 는 막습니다. 관제탑 DB 는 못 막습니다 | 막습니다 |
| 잘못된 쓰기·삭제·앱 버그 | 못 막습니다 (같이 퍼짐) | 막습니다 |
| 랜섬웨어·계정 탈취 | 못 막습니다 | 다른 계정·보존 잠금이 있으면 막습니다 |

### 어떻게 빠졌나

1. ADR-0001 은 백업을 CDC(Base Snapshot + 연속 로그)에 묶었습니다. ADR-0002 는 "ADR-0001 백업이 있으니 과거 시점 복원은 나중에 확장할 수 있다"는 전제로 범위에서 뺐습니다.
2. ADR-0004 에서 CDC 를 걷어내고 논리 복제로 바꾸면서 백업은 별도 트랙 #14 로 나갔습니다. ADR-0002 의 전제는 고치지 않았습니다.
3. #14 는 11/5 구현 없이 완료로 닫혔습니다. 같은 날 #12 의 대기 수준 표에는 "PITR(#14, 아직 없음)"으로 적혀 있습니다. 보드에서는 끝난 일로 보여 그 뒤로 다시 다루지 않았습니다.
4. 관제탑은 D-046(11/2)에서 "플랫폼 자체의 무중단은 고려하지 않는다"고 정해 처음부터 범위 밖이었습니다.

### 목표 (RPO·RTO)

#12 에서 정의한 대기 수준 표에 11/8 실측을 나란히 둡니다. 실측은 시연 준비 리허설 기록입니다.

| 수준 | 대상 | RPO 목표 | RTO 목표 | 실측 |
|---|---|---|---|---|
| 핫 레디 | 고객 서비스(demo), 클라우드 간 이전 | 계획 이전 0, 재난 시 복제 지연 | 2분 이내 | 쓰기 정지 8.8~10.4초, 이전 계획 46.6~48.8초, 누락·중복 0 |
| 핫 레디 | 노트북 온프레(demo-onprem) 장애 | 동기 복제라 0 | 25초 이내 | 전환 18.6~19.7초, 누락·중복 0 |
| 콜드 | 환경 재구축 | 마지막 백업 시점 | 수십 분 | AWS 재구축 13분 3초(11/5). **백업이 없어 데이터 복원 부분은 측정 불가** |
| 없음 | 관제탑 DB | 정의 없음 | 정의 없음 | 사본 1개 |

## 2. Decision (결정)

**복제는 그대로 두고, 그 위에 3-2-1 백업을 따로 둡니다. 시연(11/8) 범위에서는 제외하고 시연 뒤 구현합니다.**

시연 직전에 데모 기기와 DB 에 새 작업을 얹는 것 자체가 위험이라 지금은 기록만 합니다.

### 3-2-1 구성

| | 고객 DB (도쿄 A 기준) | 관제탑 DB (echo-was) |
|---|---|---|
| 사본 3 | 원본 + 매일 덤프 + WAL 연속 보관(#14 원래 범위) | 원본 + 매일 덤프 + 다른 클라우드 사본 |
| 매체 2 | 디스크(PV) + 오브젝트 스토리지 | 디스크(PV) + 오브젝트 스토리지 |
| 다른 곳 1 | GCS 서울 (AWS 와 다른 클라우드) | S3 도쿄 (GCP 와 다른 클라우드) |
| 보존 | 버킷 보존 잠금(GCS retention lock). 지금 규모는 7일로 시작, 운영이면 30일 이상 | S3 Object Lock, 같은 기준 |

### 구현 순서

1. 관제탑 DB 매일 `pg_dump` (GKE CronJob) → S3, 보존 잠금
2. 고객 DB 매일 `pg_dump` → GCS, 보존 잠금
3. 복원 시험 1회: 빈 DB 에 되살린 뒤 행 수·장부 지문을 원본과 대조하고 결과를 `docs/team/rehearsals/` 에 남김
4. 복제 긴급 정지 런북: 원본 오염을 발견하면 사본에서 `ALTER SUBSCRIPTION … DISABLE` 로 확산을 멈추는 절차와 스크립트
5. 발행에서 TRUNCATE 제외 검토 (`WITH (publish = 'insert, update, delete')`)
6. WAL 연속 보관과 PITR(#14 원래 범위)

## 3. Consequences (결과 및 영향)

### 좋아지는 점

- 잘못된 쓰기·삭제·랜섬웨어에 대해 "확산을 멈추고 어제 시점으로 되돌린다"는 답이 생깁니다.
- 관제탑 DB 를 잃어도 조직·서비스·감사 로그·보안 예외를 되살릴 수 있습니다. 시연 스냅샷 API 의 기록도 이 DB 안에 있어 지금은 DB 와 함께 사라집니다.
- 콜드 수준의 RTO 를 데이터 복원까지 포함해 측정할 수 있게 됩니다.

### 주의할 점

- **논리 복제 사본에서 덤프를 뜨면 시퀀스가 뒤처져 있습니다.** 논리 복제는 시퀀스와 DDL 을 옮기지 않습니다(ADR-0004). 사본 덤프로 복원할 때는 `setval` 로 시퀀스를 `max(id)` 이상으로 맞추는 단계가 필요하고, 스키마는 원본 기준으로 맞춥니다.
- **온프레 EC2 는 원본 A 와 같은 AWS 계정입니다**(서울 기본 VPC). 온프레 사본을 덤프 출처로 쓰더라도 결과물은 다른 클라우드 버킷에 둡니다.
- **덤프를 같은 기기에 두면 백업이 아닙니다.** 기기가 죽으면 같이 사라집니다.
- 노트북 온프레의 클라우드 사본은 EKS 파드의 임시 디스크라 백업 출처로 쓰지 않습니다.
- 비밀값(Secret Manager·SSM)과 bootstrap Terraform state(로컬 파일)는 이 결정 범위 밖입니다. 따로 목록과 복구 절차를 만듭니다.
