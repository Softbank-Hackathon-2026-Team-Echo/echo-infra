정적 데이터는 백업하고 관련 인프라는 대기시키지 않는다.
ㄴ 근데 이건 정적 데이터 한정이다. DB는 정적이 아니다.
ㄴ 그래서 기준을 하나 더 둔다. RPO랑 RTO다.
   (RPO = 복구했을 때 데이터를 어디까지 잃어도 되나, RTO = 복구에 걸려도 되는 시간)
   정적 → 백업만(대기 인프라 없음), 동적 상태 → RPO 목표에 따라 warm standby를 둘지 결정.
   (warm standby = 평소에도 꺼두지 않고 따라 돌려두는 대기 사본)
ㄴ 재난 데모라면 RPO/RTO 목표를 숫자로 박아두자. (판단 항목)

일차적으로 떠오른 관리 데이터는 다음과 같다.
1. 온프레미스의 로컬 DB 데이터
2. 플랫폼에서 관리중인 모든 컨테이너의 정보(접근 url, 배포 위치 등)
3. 퍼플릭 클라우드에서 작동중인 서비스의 DB 데이터(클라우드 DB 서비스 이용)
4. 설정 및 시크릿
5. 비정형 오브젝트 파일들
6. 네트워크 라우팅 및 인프라 권한 정보
7. CDC 파이프라인 및 동기화 오프셋 상태
   (CDC = Change Data Capture, DB에서 바뀐 부분만 뽑아내는 것)

7개의 데이터를 작업의 속성에 맞게 묶으면 다음과 같다.
- A. 계속 복제해야 하는 상태 데이터 — 1, 3, 5(바뀌는 오브젝트)
- B. 코드로 정의되는 데이터 — 2, 6(원본이 코드 상태로 관리, git / docker 등이 존재)
- C. 값의 위치만 관리하는 비밀값 — 4
- D. 파이프라인 메타 — 7
ㄴ 위의 맨 윗줄 원칙(백업만, 대기 인프라 없음)은 A에만 해당되는 원칙이다.
ㄴ B는 Git이 원본, C는 비밀 저장소, D는 offset 저장.
   (offset = 어디까지 처리했는지 가리키는 위치 값)

1번부터 구성해보자
MySQL Binlog 활성화 및 권한 분리
애플리케이션에 부하를 주는 트리거 방식 대신 내부 트랜젝션 로그를 기록하는 Binlog를 이용해
데이터를 백업한다.
ㄴ 이를 이벤트 캡처라고 하자

캡처한 이벤트를 메시지 브로커를 이용해 우리 플랫폼으로 전달한다.
이때는 redis Stream과 Consumer, Producer를 이용한다.
플랫폼이 Consumer, 온프레미스에서 이벤트를 캡처해 메시지를 생성하는 모듈을 Producer이다.

최종적으로 받은 메시지를 이용해 데이터를 백업할 클라우드 스토리지에 보내게 된다.
ㄴ 어떤 클라우드 스토리지에 보내야 하는지는 아직 정하지 않았다.
   만약 백업만을 목적으로 한다면 어디에 두던지 상관은 없을 것 같다.
   (판단 보류)

여기서 구체화할 게 몇 개 있다.
ㄴ base snapshot(기준이 되는 전체 덤프 한 장)이 없으면 복구가 안 된다.
   Binlog는 "그 시점부터 바뀐 것만 쌓는 스트림"이라, 기준이 되는 한 장이 먼저 있어야 한다.
   복구 = base snapshot + 그 지점 이후 Binlog를 순서대로 다시 적용(replay).
   그래서 백업은 두 갈래다. 주기적 snapshot + 연속 Binlog. Binlog만 쌓으면 복구가 안 된다.
ㄴ Binlog는 ROW 포맷 + GTID로 켠다.
   (ROW = 바뀐 행을 그대로 적는 포맷, STATEMENT = 실행한 SQL 문장을 적는 포맷)
   (GTID = 복제 지점을 가리키는 전역 트랜잭션 번호)
   STATEMENT로 적으면 NOW()·UUID()처럼 실행마다 값이 달라지는 쿼리가 다시 적용할 때 틀어진다.
   GTID가 있어야 "어디까지 받았나"를 정확히 끊고, 이게 그대로 7번(offset)이다.
ㄴ redis Stream은 전달 통로일 뿐이지 백업본이 아니다.
   진짜 백업본은 object storage(S3처럼 파일을 통째로 넣고 빼는 저장소)에 있다.
   Consumer group이 "어디까지 받고 확인(ack)했는지" 들고 있는 ID가 7번 offset이다.
   at-least-once(최소 한 번은 전달, 그래서 같은 메시지가 또 올 수 있음)라 저장은
   idempotent(여러 번 해도 결과가 같게)해야 한다.
ㄴ 스토리지는 백업만이면 S3/GCS 아무거나로 둬도 된다.
   단 lock-in(한 업체에 묶여 못 빠져나오는 상태)을 피하려면 S3 호환 인터페이스로 통일해두는 게 낫다(5번 참고).
ㄴ 이걸 통째로 해주는 대표 오픈소스가 Debezium이다.
   "가벼운 Debezium을 직접 만든다"로 포지션을 잡고, 직접 만들지 vs 쓸지는 판단 항목으로 남긴다.

2번
쿠버네티스 컨트롤 플레인을 일차적으로 만들어두고
에이전트로 워크로드 yaml을 만든 다음 컨트롤 플레인쪽에 저장하고 있으면 되는거 아닌가?

AWS ECR에 도커 이미지를 저장하고 쿠버네티스로 파드를 생성할 때는
워크로드 yaml만 있으면 되는데 이걸 플랫폼 ai agent로 만들게 한 뒤
git url과 ECR 이미지를 매핑하면 된다.

AWS ECR을 사용하는 것 만으로 플랫폼 종속성이 생기기 때문에
다른 클라우드 플랫폼에도 백업을 하게 한다.

여기서 구체화할 게 몇 개 있다.
ㄴ "컨트롤 플레인에 저장" 말고 Git이 원본(source of truth, 다른 데가 다 여기 맞추는 기준)이어야 한다.
   echo-infra는 Argo CD로 가기로 했으니, 워크로드 yaml은 Git에 두고 Argo CD가 맞춰 올린다(sync).
   그 Git 자체가 2번의 백업이다.
ㄴ image는 tag 말고 digest로 매핑한다. image_repository@image_digest.
   (tag = latest처럼 사람이 붙이는 이름, digest = 이미지 내용으로 만든 고정 해시값)
   latest 같은 바뀌는 tag로 매핑하면 "그때 뭐였는지"가 날아간다. (echo-was 용어 사전 공유 규칙)
ㄴ ECR 종속성 회피는 맞는 방향이고, 구체화하면 이미지 복제(replication)다.
   ECR → GCP Artifact Registry 복제, 또는 온프레 Harbor. skopeo copy나 ECR 자체 replication으로.
ㄴ 주의: "접근 url·배포 위치"는 echo-was DB가 이미 들고 있는 값이다.
   Git은 desired state(있어야 할 상태), echo-was DB는 observed state(실제로 돌고 있는 상태).
   여기 2번에서 또 저장하면 둘이 어긋난다. 저장하지 말고 echo-was를 읽자.

3번
1번과 마찬가지로 모듈을 사용하면 될 거 같다.
ㄴ 근데 "마찬가지"가 안 통한다.
   RDS·Cloud SQL 같은 managed DB(클라우드가 대신 운영해주는 DB)는
   온프레 MySQL처럼 Binlog를 같은 방식으로 못 읽는 경우가 많다.
ㄴ 대신 클라우드가 자체로 제공하는(provider-native) 방식이 있다.
   RDS면 DMS(DB 이전·복제 서비스)나 cross-region read replica(다른 리전에 두는 읽기 전용 복제본),
   Cloud SQL이면 자체 replication/export.
ㄴ 그래서 경로가 둘로 갈린다.
   1번(직접 만든 Binlog 모듈)은 온프레 self-managed(직접 깔아 운영하는) DB 전용,
   3번은 provider-native 경로. 하나로 묶으면 나중에 깨진다.

4번
이건 AWS secret manager가 있다고 한다.
ㄴ 근데 AWS Secrets Manager 하나로는 DR이 안 된다.
   AWS 전용이라, 재난으로 AWS가 죽어 GCP로 failover(죽은 쪽에서 산 쪽으로 넘기는 것)하면
   거기엔 시크릿이 없다. ECR 종속성과 똑같은 문제다.
ㄴ 구체화: 시크릿 값을 클라우드 간 안전하게 복제(gcp-sm으로 미러)하거나,
   특정 클라우드에 안 묶인 Vault(HashiCorp Vault)를 쓴다.
   secret_ref(비밀의 보관 위치를 가리키는 문자열) 포맷은 이미 aws-sm:·gcp-sm:를 지원하니,
   가리키는 위치만 바꾸고 값은 복제하는 식.
ㄴ DB엔 값 말고 secret_ref만 둔다. (공유 규칙)
ㄴ 설정(비밀 아님)은 시크릿과 분리해서 2번 Git에 둔다.

5번
클라우드 환경 간 정적 리소스 공유는 쉽게 할 수 있겠지만
온프레미스에서 정적 리소스를 어떻게 처리할 수 있을지 생각해야 할 거 같다.
ㄴ 로컬 디스크나 클라우드 리소스로 되어 있을 거 같은데
   잘 모르겠음
ㄴ 답: 온프레 로컬 디스크/NAS 앞에 MinIO를 세운다.
   (MinIO = 온프레에 직접 띄우는, S3랑 똑같이 쓰는 저장소)
   그러면 온프레도 클라우드도 똑같은 object storage로 보인다.
ㄴ 그러면 복제가 한 방식으로 통일된다. rclone이나 mc mirror 하나로 온프레↔클라우드 양방향.
   이게 들어가면 1번 백업 스토리지도 같은 인터페이스로 통일된다.

6번
네트워크 라우팅·인프라 권한은 사실 "백업"이라기보다 IaC(인프라를 코드로 정의하는 것)다.
ㄴ 원본은 Terraform 코드(Git) + state다. 손으로 만든 걸 백업하는 게 아니라 코드로 다시 세운다.
ㄴ IAM 같은 권한은 클라우드마다 1:1 복사가 안 된다. 환경별로 다시 표현해야 한다(환경 격차 매핑).
   이건 한 줄 더 파야 한다. (판단 항목)

7번
CDC offset은 1·3번을 중간부터 다시 시작할 수 있게 해주는 메타 정보다.
ㄴ 소스별로 마지막 Binlog 위치(position/GTID) + Consumer offset을 저장한다.
ㄴ 이게 날아가면 어디서 다시 시작할지 몰라 처음부터 전부 다시 맞춰야 한다(full re-sync).
   그래서 offset 자체도 안 날아가게 따로 저장하고, 아래 백업 카탈로그(10번)와 같이 둔다.

추가로 떠오른 정보 (맨 위 "다른 필요한 정보가 뭐가 있을까"에 대한 답)
8. DNS·트래픽 입구 현재 상태
   ㄴ 지금 어느 도메인이 어디로, 환경별 traffic_weight(트래픽을 몇 %씩 보내는지)가 얼마인지.
   ㄴ 재난 때 이걸 뒤집어야 하니, 복구 대상이 아니라 상시 알고 있어야 하는 상태다.
9. DB 스키마 버전 ↔ 앱 이미지 버전 정합성
   ㄴ 데이터만 복원하고 대상 앱이 다른 스키마면 깨진다.
   ㄴ 백업 시점의 schema version을 image_digest와 같이 묶어둔다.
10. 백업 카탈로그
    ㄴ 무엇을·언제·어디에·체크섬·크기. 이게 없으면 백업이 있어도 못 찾고 검증을 못 한다.
    ㄴ 7번 offset과 같이 둔다.
11. 서비스 종속성 그래프(blueprint)
    ㄴ 서비스 하나 = 어떤 DB들 + 어떤 시크릿 + 어떤 오브젝트 + 어떤 라우트.
    ㄴ 이게 있어야 "서비스를 통째로" 옮긴다. echo-ai-agent의 blueprint 추출과 바로 연결된다.
12. 정합성 기준점(RPO marker)
    ㄴ 한 서비스가 DB를 2개 쓰면 두 백업이 같은 시점으로 맞아야 복구가 일관된다.
    ㄴ 소스별 offset만으론 부족하다. "이 묶음은 T 시점 기준"이라는 공통 체크포인트가 필요하다.
