# 본선 피드백 — 재난 시 이전 우선순위, 그리고 랜섬웨어

- 날짜: 2026-11-08 (본선 시연 뒤)
- 작성: 서동옥
- 상태: 기록·분석. 구현 결정은 아직 없습니다.

## 1. 받은 피드백과 우리 생각

| 구분 | 내용 |
|---|---|
| 공식 피드백 | 정전 같은 긴급 재난에서 가장 중요한 것은 **무엇을 먼저 옮길지에 대한 우선순위**인데, 이 부분이 부족했다. |
| 우리 생각 | 우리가 만든 긴급 재난(온프레 중단 → 클라우드 이전)도 의미가 있지만, 한 걸음 더 나간다면 **랜섬웨어**가 더 큰 재난이다. 지금 구조에서는 랜섬웨어가 복제를 타고 모든 사본으로 전파된다. |

두 지적은 같은 질문으로 모입니다. 우리는 「어떻게 빨리 옮기는가」를 만들었고, 「무엇을, 어떤 순서로, 어떤 상태의 데이터를 옮기는가」는 만들지 않았습니다.

## 2. 피드백 1 — 이전 우선순위

### 2.1 지금 구조에서 우선순위가 없는 이유

| 사실 | 근거 |
|---|---|
| 서비스마다 "중요도"를 적는 칸이 없습니다. 이전 계획은 서비스 하나 단위로 만들고, 여러 서비스 사이의 순서 개념이 없습니다. | echo-was 이전 계획 모델. 코드에서 "우선순위"는 판정 근거의 우선순위(결과 행 > 쓰기 담당 확인 > 로그)로만 쓰입니다(`app/services/migration_db_cutover.py`). |
| DB 쓰기 담당을 여러 서비스가 함께 씁니다. 그래서 쓰기 전환이 일어나면 그 DB 를 쓰는 서비스가 모두 같이 이동합니다. | 관제 화면 경고 「서비스들이 트래픽 비율과 DB 쓰기 담당을 함께 써서 모든 서비스가 같이 이동합니다」. 트래픽은 11/8 부터 서비스별로 나뉘었지만(인프라 22, #113) DB 는 아직 공유입니다. |
| 도착 환경의 수용량을 확인하지 않습니다. 온프레 전체가 클라우드로 오면 도착 클러스터 노드가 모자랄 수 있습니다. | 이전 계획에 도착 측 용량 확인 단계가 없습니다. |
| 재난 자동 승인은 "옮길지 말지"만 정하고 "무엇부터"는 정하지 않습니다. | `specs/api-17-cutover-step.md` 재난 자동 승인 항목. |

결과적으로 시연 장면 ④(정전 = 노트북 온프레 중단)는 "있는 것을 전부 옮긴다"였고, 서비스가 하나뿐이라 순서 문제가 드러나지 않았습니다. 심사 지적은 서비스가 여럿일 때를 물은 것으로 이해합니다.

### 2.2 정전에서 우선순위가 특히 중요한 이유

1. **시간 예산이 정해져 있습니다.** 정전이면 UPS 가 버티는 시간 안에 일이 끝나야 합니다. 그 안에 모든 서비스를 옮길 수 없다면 무엇을 먼저 옮길지가 곧 피해 크기입니다.
2. **정전이 나면 그때는 이미 옮길 수 없는 것이 많습니다.** 전원과 네트워크가 끊긴 온프레에서 데이터를 꺼낼 수는 없습니다. 이미 클라우드에 사본이 있는 서비스만 "전환"할 수 있고, 사본이 없는 서비스는 "재구축"(이미지로 새로 띄우기)이거나 "포기"입니다. 즉 **우선순위는 재난이 나기 전에, 평소 비용으로 미리 집행돼 있어야** 합니다.
3. **도착지 자원이 한정돼 있습니다.** 클라우드도 할당량·노드 수·대역폭에 한계가 있습니다. 덜 중요한 서비스가 먼저 자리를 차지하면 중요한 서비스가 못 뜹니다.
4. **의존 관계가 있습니다.** 인증·DB·메시지 큐 같은 기반 서비스가 먼저 서야 그 위의 서비스가 동작합니다. 중요도만으로 줄 세우면 안 되고 의존 순서를 함께 봐야 합니다.

### 2.3 우리 실측값으로 본 시간 예산

11/8 실측(ADR-0005 표)입니다.

| 동작 | 실측 | 서비스가 늘면 |
|---|---|---|
| 쓰기 정지(DB 전환 한 번) | 8.8~10.4초 | DB 단위로 반복 |
| DB 포함 이전 계획 하나 | 46.6~48.8초 | 순서대로 하면 서비스 수만큼 늘어남 |
| 노트북 온프레 → 클라우드 장애 이전 | 18.6~19.7초 | 사본이 준비된 서비스에만 해당 |
| AWS 환경 처음부터 다시 만들기 | 13분 3초 | 사본이 없는 서비스의 대안 |

예를 들어 DB 를 가진 서비스 10개를 하나씩 옮기면 약 8분입니다. UPS 가 10분이라면 여유가 거의 없고, 사본이 없는 서비스 하나를 다시 만드는 데만 13분이 걸립니다. 순서를 잘못 잡으면 중요한 서비스가 시간 밖으로 밀립니다.

### 2.4 개선 방향

**(1) 서비스 등급을 등록 단계에서 받습니다.**

| 등급 | 예 | 목표 RTO / RPO | 평소 준비 (비용) | 재난 때 |
|---|---|---|---|---|
| 0 기반 | 인증, 결제, 안전 관련, 다른 서비스가 의존하는 DB | 1분 이내 / 0~수 초 | 웜 스탠바이: 클라우드에 사본 DB 와 앱이 항상 떠 있음 | 가장 먼저 전환 |
| 1 고객 대면 | 주문, 조회, 고객 화면 | 수 분 / 수 초~1분 | 파일럿 라이트: DB 사본만 상시, 앱은 0 대로 대기 | 0등급 다음에 앱 확장 |
| 2 내부 업무 | 관리 화면, 내부 도구 | 수 시간 / 수 분 | 백업에서 복원 | 0·1 등급 뒤, 자원이 남을 때 |
| 3 미룰 수 있음 | 배치, 분석, 리포트 | 하루 / 하루 | 백업만 | 재난 중에는 멈춤(자원 양보) |

이 표의 핵심은 등급이 **평소 비용**을 정한다는 점입니다. 0등급만 웜 스탠바이 비용을 내고, 나머지는 싸게 둡니다. 우선순위가 "재난 당일의 판단"이 아니라 "평소의 투자 배분"이 됩니다.

**(2) 이전 계획을 서비스 하나가 아니라 묶음 단위로 만듭니다.**

- 등급 → 의존 순서(위상 정렬) 순서로 단계를 만듭니다. 같은 단계 안에서는 병렬로 처리합니다.
- 각 단계 전에 도착 환경 수용량을 확인하고, 모자라면 3등급을 먼저 멈춰 자리를 비웁니다(부하 차단).
- 시간 예산(UPS 남은 시간)을 입력받아 "이 시간 안에 끝나는 범위"를 계획에 표시합니다. 끝나지 않는 서비스는 계획 단계에서 "이번에는 포기"로 명시합니다.

**(3) DB 공유를 풀거나, 공유 단위를 등급에 맞춥니다.**

DB 쓰기 담당이 공유되면 등급이 다른 서비스가 같이 움직입니다. 서비스별 DB(또는 DB 안의 스키마별 발행·구독)로 나눠야 등급별 순서가 실제로 지켜집니다.

**(4) 화면에서 보이게 합니다.**

- 재난 이전 화면에 "1단계 0등급 3개 · 2단계 1등급 5개 · 3등급 4개 일시 정지"처럼 순서와 포기 범위를 보여 줍니다.
- 시연이라면 서비스 3~4개(등급 0·1·3)를 두고, 정전 버튼을 누르면 0등급이 먼저 넘어가고 3등급은 멈추는 장면이 이 피드백에 대한 직접적인 답이 됩니다.

## 3. 피드백 2 — 랜섬웨어

### 3.1 왜 랜섬웨어가 더 큰 재난인가

정전·지진은 **데이터가 있는 장소가 사라지는** 재난입니다. 사본을 다른 곳에 두면 됩니다. 우리가 만든 것은 이 문제를 풉니다.

랜섬웨어는 **데이터 자체가 망가지는** 재난입니다. 사본을 다른 곳에 둬도, 사본이 원본을 충실히 따라가면 사본도 망가집니다. 「다른 곳에 살리기」가 아니라 「과거 깨끗한 시점으로 되돌리기」가 필요합니다. 팀은 11/1 회의에서 이 구분을 이미 정리했습니다(ADR-0001 은 최신 지점으로의 전환, ADR-0002 는 과거 깨끗한 지점으로의 복원). 하지만 ADR-0002 는 본선 범위에서 보류됐고, 그 전제였던 백업도 ADR-0004 에서 CDC 를 걷어내며 사라졌습니다(ADR-0005).

같은 날 회의에서 소프트뱅크 계열 IDC 랜섬웨어 사례(인프라 관리자 계정 탈취 → 대규모 암호화 → 스냅샷 복원)를 공유했습니다. 그 사례도 "관리 계정 하나가 뚫리면 모든 곳이 같이 암호화된다"는 점이 핵심이었습니다.

### 3.2 우리 구조에서 전파되는 길

**(1) 데이터 평면 — 논리 복제가 피해를 그대로 실어 나릅니다.**

| 복제 | 방향 |
|---|---|
| `echo_sub` | A(AWS 도쿄) → B(GCP 서울) |
| `echo_gcp_onprem_sub` | B → 온프레 `gcpcopy` |
| `echo_onprem_sub`, `echo_onprem_sub_aws` | 온프레 → GCP B2, AWS B2 |

모든 발행이 `FOR ALL TABLES` 기본값이라 INSERT·UPDATE·DELETE·TRUNCATE 가 모두 넘어갑니다. 공격자가 앱 계정으로 `UPDATE … SET 칸 = 암호문` 이나 `DELETE`, `TRUNCATE` 를 실행하면 몇 초 안에 모든 사본이 같은 상태가 됩니다. 복제 지연이 짧을수록(우리가 자랑한 점) 더 빨리 퍼집니다.

공격 방식에 따라 결과가 다릅니다.

| 공격 방식 | 사본으로 전파 | 이유 |
|---|---|---|
| SQL 로 값 암호화·삭제·TRUNCATE | **전파됨** | 논리 복제는 행 변경을 보냅니다. |
| 서버 디스크의 데이터 파일 암호화 | 전파 안 됨 | 논리 복제는 파일이 아니라 WAL 을 해석한 행 변경을 보냅니다. 원본 DB 는 멈추고 사본은 그 직전 상태로 남습니다. |
| 스키마 변경(DROP TABLE 등) | 전파 안 됨 | DDL 은 논리 복제 대상이 아닙니다. 대신 복제가 멈춥니다. |

디스크 암호화형이면 우리 구조가 오히려 도움이 됩니다(깨끗한 사본으로 장애 이전). 하지만 공격자가 DB 권한을 가지면 SQL 형으로 바꾸는 것은 쉽습니다. 특히 온프레 앱 DB 계정은 아직 슈퍼유저입니다(#145, 열림). 슈퍼유저는 SQL 뿐 아니라 `COPY … PROGRAM` 으로 DB 서버에서 명령도 실행할 수 있습니다.

**(2) 관리 평면 — 관제 서버 하나가 모든 환경의 열쇠를 갖고 있습니다.**

11/8 보안 감사(#134)에서 확인한 실행 신원입니다.

| 신원 | 권한 | 뚫리면 |
|---|---|---|
| echo-was 실행기 (AWS) | EKS 클러스터 관리자 | 도쿄 앱·DB 전부 |
| echo-was GSA (GCP) | 프로젝트 전체 `container.developer`, 조건부 `secretmanager.admin` | 서울 앱·DB, 비밀값 |
| 온프레 실행기 SA | 앱 네임스페이스 생성·배포, 만료 없는 토큰 | 온프레 앱 |

여러 환경으로 옮기는 서비스라 관제가 모든 환경에 손을 대는 것은 기능상 필요합니다. 하지만 그 결과 관제 하나가 뚫리면 "다른 클라우드에 둔 사본"이라는 분리가 의미를 잃습니다. 앞의 IDC 사례와 같은 모양입니다. 또 진입점 c, 온프레 EC2, EKS, 노트북 DR 감시가 모두 같은 AWS 계정에 있습니다.

**(3) 자동화가 피해를 키울 수 있습니다.**

- 랜섬웨어로 앱이 오류를 내면 헬스체크가 실패하고, 재난 자동 승인이 켜진 조직에서는 **이미 오염된 사본 쪽으로 자동 이전**합니다. 서비스는 "복구"된 것처럼 보이지만 데이터는 그대로 망가져 있습니다.
- 우리의 정합성 검사도 이 경우를 잡지 못합니다. 장부 검사(`verify.sh`)와 내용 지문 검사(인프라 25, #150)는 **출발과 도착이 같은지**를 봅니다. 둘 다 같은 암호문이면 결과는 `MATCH` 입니다. **정합성(두 곳이 같다)과 무결성(데이터가 올바르다)은 다른 질문**이고, 우리는 앞의 것만 답합니다.

**(4) 되돌아갈 곳이 없습니다.**

ADR-0005 기준으로 과거 시점 백업이 0개입니다. 복제는 있지만 모두 "지금" 상태입니다. Terraform state 의 버전 관리만 있고, 데이터 백업·스냅샷·PITR 은 없습니다.

### 3.3 개선 방향 (우선순위 순)

| 순서 | 할 일 | 막는 것 | 비고 |
|---|---|---|---|
| 1 | **변경 불가 백업** — 다른 계정·다른 자격 증명의 객체 저장소에 보존 잠금(S3 Object Lock 준수 모드, GCS 보존 정책 잠금)으로 하루 1회 이상 덤프 | 되돌아갈 곳 없음 | ADR-0005 의 3-2-1 에 "1(변경 불가)·0(복원 시험 오류 0)"을 더한 3-2-1-1-0. 관제 신원으로는 지울 수 없어야 합니다. |
| 2 | **복원 시험** — 백업에서 실제로 띄워 장부·지문 검사로 확인 | "백업은 있는데 복원이 안 됨" | 내용 지문 검사(#150)를 복원 확인에 재사용할 수 있습니다. |
| 3 | **WAL 보관과 PITR** | 마지막 백업 뒤의 손실 | 기존 spec `infra-14` |
| 4 | **최소 권한** — 온프레 앱 DB 일반 계정(#145), 관제 실행 신원을 네임스페이스 범위로, 만료 있는 토큰 | 앱 하나·관제 하나가 뚫렸을 때의 범위 | 보안 감사 #134 남은 일과 같음 |
| 5 | **전파 차단 스위치** — 짧은 시간에 대량 UPDATE·DELETE·TRUNCATE 가 생기면 모든 구독을 `ALTER SUBSCRIPTION … DISABLE` | 오염이 모든 사본에 퍼지는 것 | 감지가 복제(수 초)보다 느리면 이미 늦습니다. 그래서 1번(백업)이 먼저이고, 이건 피해 범위를 줄이는 보조 수단입니다. |
| 6 | **지연 사본** — 물리 복제 대기 서버에 `recovery_min_apply_delay`(예: 1시간)를 둔 사본 하나 | 감지 전에 퍼진 오염 | 논리 복제에는 적용 지연 설정이 없어 물리 복제로 따로 둡니다. |
| 7 | **TRUNCATE 발행 제외** — `WITH (publish = 'insert, update, delete')` | 한 줄로 표 전체가 비는 것 | ADR-0005 구현 순서 5번 |
| 8 | **무결성 신호를 이전 판단에 넣기** — 헬스체크 실패 원인이 데이터 오염이면 자동 이전을 멈추고 "복원" 경로로 | 오염된 사본으로 자동 이전 | 이전 계획 앞에 "출발이 오염됐는가"를 묻는 단계 |
| 9 | **기준선 지문** — 두 DB 비교가 아니라, 시간에 따른 같은 DB 의 지문·변경량을 기록해 급변을 감지 | 정합성은 맞지만 무결성이 깨진 상태 | #150 지문을 주기적으로 남기면 시작할 수 있습니다. |

## 4. 두 피드백을 합치면

| | 정전·지진 | 랜섬웨어 |
|---|---|---|
| 망가지는 것 | 장소 | 데이터 |
| 필요한 것 | 다른 곳의 최신 사본 | 과거 깨끗한 시점 |
| 복제의 역할 | 해결책 | 피해를 퍼뜨리는 길 |
| 우선순위가 정하는 것 | 무엇을 먼저 전환할지 | 무엇을 먼저 격리하고 복원할지 |
| 우리 현재 | 전환은 됨, 순서 없음 | 대비 없음(백업 0) |

등급(2.4)은 두 재난에 모두 쓰입니다. 0등급은 웜 스탠바이와 함께 지연 사본·변경 불가 백업을 갖고, 랜섬웨어 때도 가장 먼저 깨끗한 시점으로 복원합니다. 3등급은 두 경우 모두 멈추고 기다립니다. 그래서 다음 작업의 출발점은 **서비스 등급 칸 하나**와 **변경 불가 백업 하나**입니다.
