# [#3][consumer] Stream을 소비해 타겟에 멱등하게 반영한다

> 선행: #1(이벤트 메시지 계약). #2와 짝이지만 메시지 계약만 맞으면 병행 개발 가능. [ADR-0001](<../adr/[ADR-0001] 데이터 정합성 — 복제 시점이 아니라 복구 기준점으로.md>) 참고.
> 이 이슈는 **소비·적용 측만** 다룬다.

### 배경

Producer(#2)가 Redis Stream에 올린 이벤트를 플랫폼이 받아 타겟 저장소(복제본)에 반영한다. 여기서 플랫폼이 Consumer다.

Redis Stream은 at-least-once(최소 한 번 전달, 중복 가능)다. 즉 같은 이벤트가 두 번 이상 올 수 있다. 그래서 적용은 반드시 멱등(Idempotent)해야 한다. 그래야 중복이 와도 최종 상태가 틀어지지 않고, 놓쳐도 다시 받으면 된다.

### 설계

**1. Consumer group으로 받고, Offset을 추적한다**

Redis Stream의 Consumer group을 쓴다. "어디까지 받고 확인(ack)했는지"가 last-acked ID이고, 이것이 ADR-0001의 Offset이다. 처리에 성공한 뒤에만 ack한다.

**2. 멱등 적용**

- 대상 행은 `(source_id, table, pk)`로 찾는다.
- `INSERT`/`UPDATE`는 PK 기준 Upsert로 반영한다.
- 이미 반영한 `gtid`보다 과거의 이벤트는 무시한다(각 행 또는 소스별로 마지막 적용 gtid를 비교).
- `DELETE`는 해당 PK를 지운다.

이렇게 하면 동일 이벤트가 두 번 적용돼도 결과가 같다.

**3. 실패 시 ack하지 않는다**

적용에 실패하면 ack를 보내지 않는다. 그러면 재전달되고, 멱등 적용이라 다시 처리해도 안전하다. 한 번의 유실이 장애로 번지지 않게 하는 것이 핵심이다.

### 작업

- Redis Stream Consumer group 소비 루프.
- 멱등 Upsert/Delete 적용기.
- 소스별(또는 행별) 마지막 적용 gtid 추적.
- 처리 성공 시에만 ack.

### 완료 조건

- 같은 이벤트를 두 번 넣어도 타겟 상태가 한 번 넣은 것과 같다.
- Consumer를 중간에 죽였다 살려도 데이터가 유실되거나 중복되지 않는다.
- 적용 실패 이벤트가 재처리되어 결국 반영된다.
