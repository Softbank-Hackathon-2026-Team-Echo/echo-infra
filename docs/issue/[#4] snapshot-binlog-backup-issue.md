# [#4][backup] Base Snapshot과 Binlog를 object storage에 백업한다

> 선행: 없음(독립 착수 가능). 단 Binlog 연속 저장은 #2와 소스를 공유하므로 조율한다. [ADR-0001](<../adr/[ADR-0001] 데이터 정합성 — 복제 시점이 아니라 복구 기준점으로.md>), [데이터 정의 1·5번](<../관리해야 하는 데이터 정의.md>) 참고.

### 배경

Binlog는 "그 시점부터 바뀐 것만 쌓는 스트림"이다. 그래서 기준이 되는 전체 덤프 한 장(Base Snapshot)이 먼저 있어야 복구가 된다. 복구는 "Base Snapshot 적재 + 그 지점 이후 Binlog 재적용"이다. Binlog만 쌓으면 복구가 안 된다.

따라서 백업은 두 갈래다. **주기적 Base Snapshot + 연속 Binlog.** 둘 다 내구성 있는 저장소에 둔다.

### 설계

**1. 저장소는 S3 호환으로 통일한다**

클라우드는 S3/GCS를 쓰면 되지만, 온프레는 로컬 디스크/NAS 앞에 MinIO(온프레에 직접 띄우는 S3 호환 저장소)를 세운다. 그러면 온프레와 클라우드가 똑같은 Object Storage 인터페이스가 되고, 복제가 한 방식으로 통일된다.

**2. Base Snapshot**

- 주기적으로 전체 덤프를 떠서 저장소에 올린다.
- 덤프 시점의 GTID를 함께 기록한다(이후 Binlog를 어디서부터 이어붙일지의 기준).
- **주기 값은 RPO 목표가 정해지면 확정한다(판단 항목).**

**3. 연속 Binlog 저장**

- Binlog를 object storage에 이어서 쌓는다.
- at-least-once라 같은 구간이 다시 올 수 있으니, 저장은 idempotent해야 한다(같은 GTID 구간을 덮어써도 결과가 같게).

**4. lock-in 회피 (선택)**

백업만이 목적이면 저장 위치는 어디든 상관없지만, 특정 업체에 묶이지 않으려면 S3 호환 인터페이스로 통일해두는 편이 낫다(위 1번).

### 작업

- MinIO(온프레) 및 클라우드 Object Storage를 같은 인터페이스로 다루는 저장 계층.
- Base Snapshot 생성·업로드(덤프 시점 GTID 포함).
- Binlog 연속 업로드(idempotent).

### 완료 조건

- Base Snapshot이 저장소에 올라가고, 그 시점 GTID가 함께 기록된다.
- Binlog가 연속으로 저장되고, 같은 구간을 다시 저장해도 결과가 같다.
- 온프레(MinIO)와 클라우드 저장소를 같은 코드 경로로 쓴다.
