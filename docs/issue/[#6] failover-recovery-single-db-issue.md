# [#6][recovery] 단일 DB 서비스를 Checkpoint로 복구해 기동한다

> 선행: #4(백업 저장), #5(카탈로그·Checkpoint). [ADR-0001](<../adr/[ADR-0001] 데이터 정합성 — 복제 시점이 아니라 복구 기준점으로.md>) 참고.
> 이 이슈는 **단일 DB 서비스**의 Failover만 다룬다. 다중 소스·Managed DB는 별도다.

### 배경

ADR-0001에서 복구는 "장애가 난 서비스를 대상 환경에서 다시 가동(Failover)"하는 것이다. 살아 있는 DB를 과거로 되돌리는 원상복구가 아니다. 가장 최신의 일관 지점(Checkpoint) 위에서 서비스를 올리는 것이다.

이 이슈는 그 복구 경로를 단일 DB 서비스 기준으로 한 줄기 완성한다. 이게 플랫폼의 주 기능이고, 데모의 핵심 장면이다.

### 설계

**1. 복구 순서**

```
Checkpoint C 읽기 (#5)
  │
Base Snapshot 적재 (#4 카탈로그에서 C 직전 snapshot 선택)
  │
Binlog 재적용(Replay) → C의 GTID 지점까지
  │
서비스 기동 (앱도 C의 schema_version·image_ref로 함께 올림)
  │
검증 (체크섬·행수 대조) → 통과하면 복구 완료
```

**2. 기준점까지 "맞춰 올린다"**

대상 환경의 복제본을 Checkpoint C가 가리키는 지점까지 맞춘 뒤, 그 위에서 서비스를 가동한다(`promote to C`). 특정 저장소만 앞서가고 나머지는 뒤처진 상태로 서비스를 올리지 않는다.

**3. 데이터와 코드를 함께 올린다**

데이터를 C 지점으로 맞췄다면 앱도 C의 `schema_version`·`image_ref`로 올려야 한다. 그렇지 않으면 코드 버전과 데이터 포맷이 어긋나 깨진다. `image_ref`는 Digest로 고정돼 있어 "그 시점에 무엇이 떠 있었는지"를 정확히 재현한다.

**4. 검증까지가 한 세트다**

복구가 "됐다고 가정"하지 않는다. 복구 후 체크섬과 행수를 카탈로그 값과 대조해, 기준점대로 올라왔는지 확인한다. 검증을 통과하지 못하면 그 복구는 실패로 처리한다.

### 작업

- Checkpoint·카탈로그를 읽어 복구 대상 Snapshot과 Binlog 구간을 고른다.
- Snapshot 적재 → Binlog를 C까지 Replay.
- 서비스 기동(앱 이미지·스키마를 C에 맞춤).
- 복구 후 체크섬·행수 검증.

### 완료 조건

- 백업만 있는 상태에서, 단일 DB 서비스를 대상 환경에 Checkpoint 지점으로 복구해 기동할 수 있다.
- 복구된 데이터의 체크섬·행수가 Checkpoint 기준과 일치한다.
- 앱이 C의 이미지·스키마로 떠서 정상 동작한다.

### 이번에 하지 않는 것

- 다중 소스(DB 2개+) 서비스의 조율 복구.
- Managed DB의 복제본 승격(provider-native).
- 트래픽 전환·무중단 데모 연출(이전 엔진 쪽 별도 트랙).
- 논리적 재해(과거 clean 지점 Restore) — ADR-0002.
